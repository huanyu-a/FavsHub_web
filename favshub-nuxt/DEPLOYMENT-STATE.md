### 1.0.100：清掉门禁自身的三个尾巴（端口 / openssl / UI 接线）（2026-11-09）

用户明确要求「不要给我留这些奇奇怪怪的问题，我只要结果」，于是把上一轮结尾列出的
三条「接受现状」**全部做掉**。它们都不是运行时功能，而是**门禁自身的可靠性**问题 ——
共同特征是：出问题时**报出来的错指向别处**，让人照着错误提示去改反而更糟。

**① 17 个套件的硬编码端口 → 运行时挑端口 + 冲突即换端口重试**

`assertion-count` 里 **17 个**套件把监听端口写死（3210 / 3211 / 3212 / 3218 / 3255 / 3257 /
3258 / 3261 / 3262 / 3264 / 3265 / 3266 / 3267 / 3269 / 3270 / 3272 及一个 mock 端口）。
本机只要有**残留实例**占着那个端口，新起的应用立刻 `EADDRINUSE` 死掉，而报出来的是
「断言数回归」或「文档数字不符」—— 指向的都不是真因（上一轮我就因此误判过一次）。
更隐蔽的是：先前那版 `pickFreePort()`（绑 `:0` → 拿号 → 立即释放）**自身有竞态**，
释放到应用真正 `listen` 之间可能被别的进程抢走。

新增 `scripts/lib/free-port.mjs`：`pickFreePort()` / `isPortConflictError(...evidence)` /
`startWithFreePort(start, { attempts, onRetry })`。判据**只认端口冲突的证据**
（`EADDRINUSE` / `address already in use` / Windows 同义文案 / 本仓库 `端口 N 仍被占用`），
其它错误**立刻抛出** —— 否则真正的故障会被重试拖成 5 倍超时、病因也被埋进重试日志。
配套单测 `scripts/lib/free-port.test.mjs`（**19 项**，含 4 条**反例**：ABI 不匹配 / 未就绪 /
`ECONNREFUSED` / `EACCES` 都必须**不**判为端口冲突）。

顺带修掉两处「不修则重试永远不会触发」的问题：就绪探测补 3s 超时（遇到「接受连接但
不回响应」的占位者，原来的 `fetch` 会**永挂**，30s / 40s 上限根本到不了）；
4 个套件补 early-exit 检测并把子进程 stderr 带进抛出的错误（端口冲突的证据只在 stderr 里）。

**竞态是真验过的，不是「应该没问题」**：后台真起一个进程占住端口 → 判据拿到真实 OS 错误
→ 换到内核新分配的端口并真的 `listen` 成功；再用真实套件的副本做端到端（注入「第一次
选到被占端口」），日志为 `↻ 第 1 次起应用失败（端口 34570 被占），换端口重试 → 42491`
→ `15 通过 / 0 失败`、exit 0。

另外把两处**恒真断言**（`护栏1 端口空闲`，判据是字面 `true` —— 等于没测）改成能证伪的
「答话的是我们自己起的进程」（依据：同一时刻一个端口只能被一个进程绑定；若是残留实例，
我们的子进程早就 `EADDRINUSE` 退出了）。变异验证：把子进程句柄置空 → 如实报红并打印
`pid=undefined exitCode=undefined`。

**② `ssrf-pin-check` 的 TLS 靶标不再依赖 `openssl`**

原先运行时用 `openssl` 现场签一张自签证书。当时的处理是「缺 openssl 就报红、拒绝静默跳过」
（那是对的），但留下一个更隐蔽的问题：**「没有 openssl 时那条分支到底对不对」在装了
openssl 的机器上永远没人验证**。现改为仓库内固定 fixture
（`scripts/fixtures/tls-pinned-test.{crt,key}.pem` + README），那条分支**被整个删掉**：
任何有 Node 的环境行为完全一致。自证：
`env -i PATH=/tmp/emptybin node scripts/ssrf-pin-check.mjs` → **18 通过 / 0 失败**。

同时补一条**证书过期即报红**的断言（读 `notAfter`）—— 否则 2036 年那天会以
「TLS 校验失败」的形式莫名报红，与要验的机制毫无关系。变异验证：换成 1 天期证书 →
`✗ 固定 TLS fixture 尚未过期 … notAfter=Nov 10 10:31:31 2026 GMT`。

**③ UI 接线层补上守卫（独立审查指出的「另一半」）**

上一轮只补了「参数构造」那一半。剩下这半截（控件 ↔ 状态 ↔ 参数 ↔ 白名单）有一类
**不报错、只静默失效**的坏法：`v-model="dealsCatgory"` 拼错一个字母，Vue 会把它当成一个
**新变量** —— 下拉照样能选、界面毫无异常，但它根本没进筛选状态，列表永远不动，
表现与「后端没实现这个筛选」一模一样。新增 `scripts/admin-filter-wiring.mjs`（**46 项**）
把四条链一起对账：

```
模板控件 ──v-model──▶ 脚本状态 ──▶ 该视图的 filterState ──▶ ADMIN_DEAL_FILTER_FIELDS
                                                                    │

```

并顺带清掉一处真隐患：**发布者白名单原本有三份副本** —— 服务端写在路由文件里的局部常量

界面就筛不出来；界面改个词，`pickEnum` 认不出 → 降级成「不筛」，同样是静默。
现已收敛到 `utils/deal-fields.ts`（`ORIGIN_FILTERS` / `ORIGIN_OPTIONS`），服务端与两处下拉
共用同一张表；并加断言「筛选栏里不许再出现手写的非空 option」。
浏览器复验：两处「发布者」下拉仍渲染 全部 / 游客 / 注册用户，选「游客」→ **5 条**
（与种子算术一致）。

判据本身修过两次，都是**自己踩的坑**，已写进注释：① 模板里有嵌套 `<template v-if>`，
用 `indexOf('</template>')` 会把模板在第 237 行截断，「全部」卡片根本没进解析范围；
② 「修改建议」那张卡片用的是 `v-if` 而非 `v-else-if`，只匹配后者会漏掉它。

### 1.0.98 之后的门禁自身修正（2026-11-09，随 1.0.99 一并发版）

以下都是**门禁自己的缺陷**，不改任何运行时行为 —— 因此当时刻意**没有**为它们单独
bump `VERSION`、也没有单独重发镜像（那些修正最终随 1.0.99 这次功能性发版一并上线）。
结论以一次**独立只读审查**收尾（该审查逐条复核、自己做变异注入与端口占用复现、
全部按字节还原并校验 md5）；下面带 ⚠️ 的两处正是它推翻我原说法的地方。

**1. `ssrf-pin-check` 的 TLS 断言依赖公网 → 断言数抖动 + 覆盖静默消失**

原第 3 组连真实公网（`https://one.one.one.one/` 钉 `1.1.1.1`）。两个毛病：

- 断网/抖动时走 `else` 只打印 `⚠ https pin 未验证` 就过去了 → 实测连续三次跑，
  总数在 **2108 / 2107 / 2108** 之间浮动。而 `assertion-count --check` 会把它报成
  **「文档数字不符，请更新后再提交」**—— 照那个提示去改文档，恰好把真实覆盖丢掉。
- 判据是 `status < 500`，**只能证明「连上了」**。若有人把证书校验关掉
  （`rejectUnauthorized: false`），原测试**同样会通过** —— 而它自称防的就是
  「用一个漏洞换另一个漏洞」。

改为**本地自签证书靶标 + 正负两例**（当时是运行时 `openssl` 现生成；2026-11-09 已改为仓库内固定 fixture，见「1.0.100」一节，全程离线确定性）：
正例证明 pin 之下 SNI/主机名校验照常工作；**负例**（主机名与证书不符必须被拒）
才真正证明校验没被关掉。断言数 12 → 13，连跑五次稳定 13/0。
反向验证：把校验改成 `rejectUnauthorized: false` 后，正例仍绿、负例如实报红。

> ⚠️ **上面这句「反向验证」是我当时的过度声称，2026-11-09 被独立审查推翻。**
> 负例注入的是**本套件自己那份复刻件**（`pinnedRequest`），而该套件**不 import 生产代码**。
> 审查者改的是**生产源码** `server/api/token-deals/fetch-models.post.ts` 的 `requestOnce`，
> 结果套件 **13/0 全绿、毫无反应** —— 也就是说「关掉证书校验」这个回归在**真实出站路径**上
> 仍然无人守，我却把它写成已经被守住。
>
> 已补 3 条**源码漂移**断言（该文件的第 6 组本来就是干这个的，只是漏了这几项）：
> 禁 `rejectUnauthorized: false`、禁空 `servername`（会连带废掉 SNI 主机名校验）、
> 必须经 `lookup` 把已校验地址钉上。断言数 13 → **16**。
> 反向验证（这次是对的方向）：往生产源码注入 `rejectUnauthorized: false` →
> `✗ 真实源码未关闭证书校验`，退出码 1；源码按字节还原（md5 一致）。
>
> 教训：**「复刻测试」与「源码漂移断言」是两件事**。复刻只能证明「这个写法管用」，
> 证明不了「源码里真这么写」。凡是靠复刻验证的安全属性，都必须另有一条钉住真实源码。

**2. `assertion-count --check` 把「套件挂了」误报成「文档写错了」**

原实现无条件调 `checkDocs(total)`。于是某个套件起不来时，总数偏小，
它先打印「文档写的 2109，实测 2002 —— 请更新后再提交」。
实测踩过：本机一个临时实例占住 3266，`state-machine` 起不来，报的就是这条误导信息。

现在有套件未通过时**明确拒绝校验文档**，并说明「总数偏小是套件挂了，先修套件」。

**3. 套件端口硬编码 → 被占用时伪装成断言数回归**

`state-machine` 原硬编码 `3266`（注释称「独占端口」），假设「没别的东西用它」。
该假设不成立：任何残留进程都能占住它。现改为运行时绑 `:0` 让内核分配空闲端口。
反向验证：**故意占住 3266** 再跑，套件仍 **107/0 通过**。

**4. 后台「已失效」面板筛选：补上真正的回归保护（+83 项）**

筛选功能（分类/品质/地区/来源/发布者/失效原因/关键词 + 三档 chip 计数）此前只有一份
**活在 `/tmp` 的手工脚本**，且依赖本机 `data/favshub.db` 副本 —— CI 里没有那个库，
等于**上线后零回归保护**。

现收进仓库为 `scripts/admin-invalid-filters.mjs`（自建临时库 + 自播种 30 行，
覆盖每个筛选档位），并接入 `assertion-count` 与 CI。期望值**不来自后端**
（先取全量、客户端自己重算），否则就是「用实现验证实现」。

变异测试确认它不是假绿（三处注入均被精确捕获、退出码 1）：

| 注入的缺陷 | 套件反应 |
|---|---|
| `category` 筛选静默失效（接口仍 200） | `category=token（期望 6 条）— api=24/24`，5 项报红 |
| chip 计数忽略筛选（回到「chip 说 15、列表说 2」） | `origin=guest 下 deleted 分档计数 — 8 vs 4` 等 5 项报红 |
| `search` 不做 LIKE 转义（`%` 通配符注入） | `search=% 被当作字面量 — api=24 expect=1` |

另修一处**真空用例**：初版播种把 `category` 与 `region` 挂在同一个 `i % n` 循环上，
于是 `category=cloud` 恒为 `region=cn`，「cloud+global」组合永不为真 —— 测试自己报了出来。
现各维度用错开的循环下标，并新增「每个档位/组合都有命中（无真空用例）」断言。

**5. `second-batch-e2e` 里一条「判据与断言名相反」的假绿**

原断言名为「公网字面量走到了连接阶段（报错**不是**「地址格式」类护栏拦截）」，
判据却是 `/内网|不是 JSON|模型清单接口|无法连接|响应超时/` —— 而护栏拒绝时的文案正是
「**不允许访问内网地址**」，含「内网」。也就是说**护栏误拦公网地址时它照样通过**，
它检测不了自己名字里声称的那个回归。

收紧成「不许出现护栏文案」后**当场报红**，实测到的正是 `{"error":"不允许访问内网地址"}` ——
原因是本机 fake-ip DNS 下 `1.0.0.1` 会被重定向到 `one.one.one.one`，该主机名解析进
`198.18/15`（基准保留段）而被**正确地**拦下；而同一台机器另一时刻实测到的是「响应超时」。

结论：**本机无法稳定制造「公网字面量走到连接阶段」这个状态**，这条 e2e 断言证明不了那件事。
故改为只断言「未触发 5xx、给出可读的 400」，并在命中护栏文案时打印一行说明本次实际路径。
「公网地址不得被误判为内网」这条不变式由**确定性**的 `private-ip-check.mjs`（公网清单
`1.1.1.1`/`8.8.8.8` + 各内网段紧邻边界）守着，不依赖网络、不因 fake-ip 摇摆。

### 1.0.98：审核队列换「请求序号守卫」（2026-11-09）

`loadDeals()` 原先是 `loadingGuard`：**有请求在飞时后来的直接 return**。它挡住了竞态，
代价是更隐蔽的一种错 —— 新筛选条件被**静默丢弃**（分页按钮的 `:disabled` 只按页码边界判断、

列表停在第 2 页而页码高亮已是 3。另注：本文件早版把成因写成「`watch(page)` 与手动改状态双触发」，
那是错的 —— 该页**没有** `watch(page)`，`grep watch` 只命中那条注释自身。
筛选条显示新值、数据是旧值，看起来像「筛选没生效」）。
改为与 `loadInvalid()` 同一口径：请求照发，只让**最新一次**的响应落地。

| 探针 | 结果 |
|---|---|
| 连点两次「下一页」（各 +400ms 时延） | 页码 3、列表随之翻页 ✓（旧实现下第二次点击被吞） |

### ⚠️ 更正：上一版我把它记成「线上泄露」，其实是**探针假阳性**（本轮查清）

1.0.97 部署后 `post-deploy-verify` 报 `public-field-matrix` 2 项失败，我当时的结论是
「`/tokens/keys` 泄露内部字段 `source_url`，先前就存在」。**那个结论是错的**，
错在没先看对外契约就按字段名定罪。本轮取证：

| 证据 | 结论 |
|---|---|
| `favshub-data-ops/SKILL.md` 的 `GET /api/token-keys` 18 字段白名单 | **明确包含 `source_url`** —— 它是对外契约字段，不是内部列 |
| `git log -S` 该端点字段清单 | 自 `42e302b`（1.0.15 上线）就在下发；`33939ca`（1.0.80）修的是**遮蔽值里的 key 形态串**，不是删字段 |
| 线上 29 行逐值 `containsKeyLike` | **0 行值含密钥形态**（真泄露会是这个形状） |
| Key 页可见文本 / 整页 HTML | 零命中密钥形态；`source_url` **确实被前端消费并渲染**（`components/tokens/TokenKeyCard.vue:372` 造 `safeSourceUrl`，`:104-106` 与 `:132-134` 两处渲染成 CTA 的 `href`）—— 这反过来证明它是必须在的契约字段：删掉会直接断归因链 |
| 语义 | `token_deals.source_url` = 情报来源留痕（公开侧永不下发）；`token_keys.source_url` = 原帖地址（对外归因）。**两张表的同名字段，语义相反** |

所以：自 `3379cf8`（1.0.72）把 `source_url` 列进 `INTERNAL_KEYS` 起，`token-keys` 端点与
Key 页这两档**恒为失败** —— 一条长期挂红的假断言，正在本文件自己警告过的
「训练人忽略脚本输出」那种坏味道。

**修法（`scripts/public-field-matrix.mjs`，纯测试改动，不发版）**：不是删字段、也不是加
全局 `allowKeys` —— 那两招会顺手把 `token_deals` 那条**真**探测器弄瞎（它防的正是
`...row` 展开全列重新漏出这一列）。改为**按端点豁免** `opts.publicFields`：

- 只有 `/api/token-keys` 与 `Key 页` 传它；`/api/token-deals` 那三档与列表页**照旧严格**；
- 豁免的只是「键名不得出现」；这些端点**仍逐值**查密钥形态，且**键缺席要报**
  「出口白名单被删？归因链会断」—— 双向都守住，不是单向放宽；
- 命中时打印**先脱敏再截窗**（`maskedPeek`），绝不把明文 Key 打进控制台/CI 日志；
- 判定函数直接 `import` 真源 `utils/key-redact.ts`（与 `category-source-check.mjs` 同法），
  避免「拦的规则」与「脱敏的规则」再次漂移 —— 那是 1.0.86 记过的同一类事故。

**反向验证**（只看到 18/0 不能证明没弄瞎，必须人为造一次泄露看它咬不咬）：
临时假服务端三种模式，跑**同一个探针** ——

| 模式 | 注入 | 探针反应 |
|---|---|---|
| `deals` | `/api/token-deals` 与 `/tokens` 页漏出 `source_url` | 4 档全部如实报红「泄露 source_url」✓ 没瞎 |
| `keys` | `token-keys` 的**公开** `source_url` 值里夹带 `sk-`+40 字符 | `Key 页` 与 `token-keys` 两档报红，预览为**脱敏后**的 `sk-aaa…aaaa` ✓ |
| `clean` | 与生产同形 | 0 泄露类失败 ✓ |

生产复跑：**18 通过 / 0 失败**（改前 15/2）。

> 顺带：我第一版修法把它做成**全局** `PUBLIC_FIELDS` 豁免，结果给 collections / prompts /
> tags 等 8 档凭空加了「缺公开字段」—— 又一轮自己造的假阳性。教训与 1.0.72 那条同源：
> **豁免必须钉在具体的端点上，不能按字段名全局生效。**

### 🐞 1.0.88 修的两个「门禁自身」缺陷（比被测代码的 bug 更值得记）

**① 门禁容忍套件失败 —— 而「门禁 exit 0」是全项目唯一的绿灯信号**

`assertion-count.mjs` 记录了每个套件的 `exit code`，会打印 `⚠ exit N`，但**从不影响退出码**：
末尾只有 `return checkDocs(total)`（校验文档数字）和 ABI 不匹配才 `process.exit(1)`。
也就是说某个套件挂了，门禁照样绿 —— 唯一症状是「总数少了几项」，然后文档校验失败，
报出来的还是「文档数字不符」而不是「某某套件挂了」。**误导方向恰好相反。**

已修：任何套件 `exit !== 0` 或断言数无法解析，门禁即 `exit 1`，并打印该套件的
`✗` 行与失败明细（各套件明细格式不统一，按「✗ 行 → 缩进的 `- 原因` → 末尾非空行」三级取）。
**牙齿验过**：注入一条干净失败 → `✗ 1 个套件未通过：── private-ip-check（exit 1，只解析到 102 项）──`
＋ 该失败原文，退出码 1。

**② `ssrf-pin-check` 约 5% 假红（此前被我误判为「一次性网络抖动」）**

它有一条基于时限的断言：`elapsed < 3500`（硬定时器配 2000ms）。实测**复现 2/40**：

```
✗ 修法：硬定时器让慢速响应在配置时限内被掐断  实测 3615ms err=timeout
✗ 修法：硬定时器让慢速响应在配置时限内被掐断  实测 3665ms err=timeout
```

注意 `err=timeout` —— **硬定时器确实生效了（修复本身是好的）**，只是 `req.destroy()` 之后
错误事件的到达还受响应流影响，实测会落到 3.6s 左右，超过那个 3500 的魔数上界。

改判据为 `newWay.err === 'timeout' && newWay.elapsed < 5000`：
`err === 'timeout'` 才是真正的不变量（靶标每秒吐字节，空闲超时同为 2000ms 却永不触发，
所以这个 'timeout' 只可能来自硬定时器），上界对齐 6000ms 竞速预算才有意义。
**修复后连跑 60 次 0 异常**（修复前 2/40）；**且牙齿仍在** —— 抽掉硬定时器即
`实测 6002ms err=__still_running__` 报红。

> 教训：**门禁自身的缺陷比被测代码的 bug 更隐蔽** —— 前者会让人以为「绿灯 = 没问题」。
> 一条机器速度相关的魔数上界，代价是 5% 的随机红；而一个不设防的退出码，代价是
> 真的失败被当成通过。

### ✅ 已修（1.0.93）：游客订阅的读写限流键没做 IPv6 /64 聚合

`index.post` 一开始就用 `rateKeyForIp(ip)` 把 IPv6 收敛到 /64，注释也写明理由：
「否则换一个地址就能重置配额」。但 `[token].get/patch/delete` 三个端点用的是
**原始地址**（`getClientIP(event)`）—— 同一个 /64 内换地址就能重置 60 次/小时的配额。

影响有限（那个限流是防「拿 token 当探针刷 404」，而 token 是 256 bit 随机、本来就暴力不出来），
但它与同模块自己的注释自相矛盾，且方向是**更松**。改成与 `index.post` 一致。

**这一处最容易搞反方向**：把 IPv6 收敛到 /64 是**收紧**（同一个 /64 的人共享配额），
所以必须同时验证「不同的 /64 拿到独立配额」—— 否则「共享」也可能只是因为限流本来就是全局的，
那样断言就毫无意义。套件里这两条正反断言都在（30 + 30 + 第 61 次 → 429；换 /64 → 404）。

**牙齿验证**：把三处退回 `getClientIP(event)` 后 →

    ✗ 同 /64 第 61 次 → 429（累计配额共享，换地址不能重置） — status=404
    → 52 通过 / 1 失败

### 🔍 查证（1.0.94，未发现漏洞）：SSR head 的注入面

`<head>` 里混着两类**不受信字符串**，任一处漏转义就是存储型 XSS：

| 来源 | 可控者 | 落点 |
|---|---|---|
| `siteTitle` / `siteDescription` / `siteKeywords` | 管理员（`system_config`） | `titleTemplate` + 一串 `meta[].content` |
| 通告 `title` / `provider`、精选集 `name` / `meta_title` / `meta_description` | **普通用户**（建通告/建精选集） | 详情页 `<title>`、`og:title`、`description` |

实测（临时库种入含 `" < > /` 的恶意载荷）**全部落点转义正确，0 处可破出**。
所以这一轮**没有修复**，产出的是一个回归护栏套件。

#### unhead 的转义是**按上下文分派**的（这是最值得记住的一点）

    escapeHtml(str)        // & < > " ' / 全部转义 —— 用于 <title> 内文（RCDATA 上下文）
    encodeAttribute(value) // **只转义 "**          —— 用于属性值

属性那一侧只转义双引号，看着「不全」，实际是**充分且最小**的：
按 HTML 规范，带引号的属性值里的 `<`、`>` 是惰性文本，分词器根本不会在那里起标签 ——
所以我实测看到的 `content="prov&quot;><script>alert(1)</script> …"` 里那个裸 `<script>`
**无害**。

由此得到一条必须钉住的**潜伏前提**：`encodeAttribute` 只转义双引号，
所以属性值**必须始终用双引号包裹**。一旦有人把值改成单引号或不加引号，这个转义就不够了。
套件里有一条断言用分词器统计每个属性的引号风格来守它。

#### 我在这一轮把判据写错了两次（都记下来）

1. **第一版用 `html.includes('<script>alert(1)</script>')` 判「未转义」→ 3 个假阳性。**
   「原始串是否出现」不是判据。正确判据是两条：元素文本上下文里不许有裸 `<`；
   `content="…"` 的捕获必须**容纳整个载荷**（若引号没被转义，捕获会在那里被截断）。

2. **改用正则数「真标签」→ 又把属性值里的 `<script>` 数成了标签。** 这正是第 1 条错因的翻版。
   于是写了一个**遵守引号状态的极小分词器**，并加了一条决定性判据：
   去掉真标签与 `<title>` 内文后剩下的文本里不许有载荷 —— 这一条能抓到注入的**裸 `<script>`**，
   而标签白名单抓不到它（head 里本来就有合法的 `<script type="application/json">`）。

3. 补「属性必须双引号」那条检查时，**我又用了正则**，于是 `content="width=device-width, initial-scale=1"`
   里的 `initial-scale=1` 被误判成「无引号属性」。改回分词器后又发现 `<link crossorigin>`
   是**布尔属性**（根本没有值），需要与「有值但无引号」区分开。

#### 判定器自带牙齿

写错的判定器会让所有断言永远绿。所以第 1 组先拿**已知安全**与**已知危险**的样本给判定器做自检
（8 项）：危险样本必须被抓出并指出是哪个标签/属性，安全样本必须放行。判定器坏了，第 1 组立刻红。

**端到端牙齿验证**：把构建产物里 unhead 的 `escapeHtml` 与 `encodeAttribute` 都改成恒等函数后 →

    ✗ 通告详情页 meta[description] 的捕获容纳了整个载荷（引号已转义） — 捕获="prov"
    ✗ 通告详情页 标签之外的文本里没有载荷残留 — 命中处="…})() alert(1) 的免费额度通告…"
    → 28 通过 / 13 失败

#### 另一个坑：空洞断言

种入的值**必须真的到达 head**，否则「没有破出」是全绿但毫无意义的。实测 `/tokens` 列表页
就是如此 —— 页面级 `useHead` 覆盖了 TDK，TDK 压根没进 head。所以每组都断言载荷确实到达，
且全局要求到达落点数 ≥ 5。这条控制在实测中当场如实报了「断言会空洞」。

### 🐞 1.0.95 修的「覆盖假象」：两个 AI 套件写好了，却从来没有被执行过

清点 `scripts/*.mjs` 与门禁/CI/`package.json` 的交叉引用时发现 **28 个脚本不在任何执行路径上**。
其中多数是数据工具/生成器（`seed-*`、`gen-*`、`copy-*icons`、`import-*`）—— 那没问题。
但有两个是**真正的测试套件**：

| 脚本 | 行数 | 覆盖 | 被谁跑过 |
|---|---|---|---|
| `ai-api-smoke-read.mjs` | 526 | 122 项 | 只被 write 套件当助手引用 |
| `ai-api-smoke-write.mjs` | 667 | 123 + 8 项 | **没有任何东西引用** |

它们覆盖 30 个 `/api/ai/**` 端点与 `/api/mcp`：令牌创建与展示安全、**通道隔离（PAT ≠ JWT 双向不承认）**、
scope 分级（read 令牌不可写/删）、MCP 的 `initialize`/`tools/list`/`tools/call` 与权限一致、
书签/文件夹/提示词/标签/通告的写删与跨用户隔离、`dry_run` 不落库、审计日志绝不记录请求体。

**它们是通过的**（实测 122 / 123 / 8 全绿）—— 但从来没有任何一次构建执行过它们。
这就是「有测试 ≠ 有保障」：`/api/ai/*` 一旦回归，门禁与 CI 都不会响。

#### 它们为什么没被接进去

它们是**黑盒烟测**（`process.argv[2]` 收 BASE），自己不启应用，还需要特定环境：
放开注册（`allow_registration=true`）、关掉注册人机校验（`register_turnstile_enabled=false`）、
`NUXT_ADMIN_USERS=smokeadmin`、`NUXT_TRUST_PROXY=true`。

更关键的是写套件有**两种互斥模式**，套件作者自己在注释里论证过：

- 常规模式（第 0~5、7 节）：每令牌打 40~90 个 AI 请求，必须**放宽** `FAVSHUB_RL_AI_*`
- `--limit` 模式（只跑第 6 节）：要验证「第 N+1 次才 429」，必须用**默认**配额

两者不能在同一进程里共存 → 新增编排器 `ai-api-gate.mjs`**分两次启服务**，把配方固化下来。

#### 编排器的六道护栏（其中第三条是关键）

1. 端口必须先空闲（3210）—— 否则测到残留实例
2. 每个阶段 PASS 必须 > 0 —— 空跑不算成功
3. **`--limit` 阶段不许出现「跳过限频压测」的 WARN**
4. read 阶段输出里必须真的出现过 `favs_ai_` 前缀 —— 证明 PAT 通道真被走过了
5. 输出里不许出现未捕获异常 / `ECONNREFUSED` —— 防「脚本崩了但 PASS=0 当成没事」
6. 临时库用完即删

#### 第 3 条为什么必须有（一次实测）

套件在配额被覆盖时会打 `[WARN] … 跳过限频压测` 而**不是**失败。我故意给会话B 也放宽了 AI 配额：

    · ai-write-limit      4 项  退出码 0        ← 套件自己：退出码 0，看起来是绿的
    ✗ --limit 阶段没有出现「跳过限频压测」的 WARN — 出现跳过 WARN
    → 265 通过 / 1 失败

**限流那一节（8 → 4 项）被静默跳过，而套件退出码仍是 0。** 只有这条护栏抓到了它 ——
否则「全绿」是空的，限流回归谁都发现不了。

#### 顺带记一个脚手架坑

#### 「显然的修法」是错的 —— 本节最该记住的一段

最直觉的修法是「名字里含 `password`/`secret`/`key` 就过滤」。**实测证明它会误杀**：
生产 settings 出现过的 27 个键里有一个叫 **`showPasswordsLink`** —— 那是扩展的
「显示密码链接」**UI 开关**，值是个布尔。按名字过滤会把它摘掉，破坏扩展同步。

真正安全的是**按值**判断（`scrubSecretValues`）：名字可以随便起，值的形态骗不了人；
`showPasswordsLink` 的值是 `true`，天然不会命中。

对现存数据是 no-op：27 个键的值全是布尔/短字符串，没有任何一个命中 `containsKeyLike`。
它只在真的有人写入密钥时起作用 —— 不会因为「防未来的事」弄坏现在的功能。

#### 另一处关键测量：遮蔽形态不匹配 `KEY_LIKE`

「按值扫」成立的前提是**遮蔽值不会被误判成密钥**。实测 `key_masked = "sk-probe…wxyz"`
**不**匹配 `KEY_LIKE`（`…` 不在 `[A-Za-z0-9_-]` 里，`sk-` 之后只有 6 个字符，不足 `{8,}`）。
否则按值扫会满屏误报、根本没法用。这条前提也写成了套件里的一条断言，
将来前缀规则若改动导致它失效，会当场报出来。

### 🔒 客户端真实 IP 的可信链：两条**不能碰坏**的部署事实（2026-11-05 查证）

全站的「一人一票 / 按 IP 限频 / 游客去重」都建立在**客户端 IP 可信**之上，而这条链
**不在代码里，在部署里** —— 代码侧怎么改都保不住它，nginx 配置或防火墙改一行就可能全废：

```
公网 → 宝塔 nginx(443/80，宿主机进程) → 容器 nginx(3090) → 应用(:3000)
                    │                          │
                    │ 追加真实 IP 到 XFF 末尾    │ 用 $remote_addr 覆盖 X-Real-IP
                    ▼                          ▼
        X-Forwarded-For: <伪造>, <真实>    应用只认 X-Real-IP
                                              （因为直连对端是内网，见 getClientIP）
```

**事实 ①：容器 nginx 必须用 `$remote_addr` 覆盖 `X-Real-IP`**，且 realip 三件套齐备
（`set_real_ip_from` + `real_ip_header X-Forwarded-For` + `real_ip_recursive on`）。
`real_ip_recursive on` 是关键：它从 XFF **右侧**取第一个非可信地址，所以客户端自己塞在
XFF 里的伪造值会被宝塔追加的真实 IP 顶掉。

**事实 ②：映射出去的 3090 绝不能对公网可达**（现由一条 DOCKER-USER 规则兜住）：

```
-A DOCKER-USER -i eth0 -p tcp -m conntrack --ctorigdstport 3090 -j DROP
```

**为什么 ② 是必需的 —— 实测过，不是推理**：直连 `127.0.0.1:3090` 并带
`X-Forwarded-For: 203.0.113.77` 时，容器 nginx 的访问日志里 `$remote_addr`
**就是 `203.0.113.77`**。因为对公网直连时链路里没有宝塔那一跳，XFF 里只有客户端
自己写的值，realip 只能采信它。**一旦 3090 对外暴露，任何人都能声称自己是任意 IP**，
事实 ① 的保护形同虚设。（宝塔经 `127.0.0.1:3090` 回源走 loopback，不匹配 `-i eth0`，正常放行。）

**怎么随时复查**（这两条此前没有任何检查，改坏了没人会知道）：

```bash
# 在服务器上跑（需要 docker + iptables，因此不进 CI）
bash scripts/verify-edge-ip-integrity.sh https://hao.bx9y.com.cn
```

它会：解析 nginx 配置确认**承载 `/api` 的 location** 都覆盖了 `X-Real-IP`
（纯静态路径如 `/favicon.ico` 不覆盖是无害的 —— 限流中间件第一行就是「非 `/api` 一律 return」）；
确认 3090 有丢弃规则；然后**行为验证**两端 —— 本地直连的伪造应被采信（证明确实需要 ②），
公网链路的伪造必须被真实 IP 顶掉（这是真正的安全断言）。非 0 退出 = 有断言的防线已破。

**踩过的坑（写脚本时）**：生产 `nginx.conf` 是 **CRLF** 行尾。不剥掉 `\r` 的话，
按 `$NF` 解析 `location ... {` 会得到 `"{\r"`，location 路径被解析成裸回车 ——
**不报错，但分类全错**（安静地错，比报错更糟）。脚本里已 `tr -d '\r'`。

### ⚠️ 状态字段 `state`：运维必读

**七档取值**，只有 `published` 对外可见：

    pending(待审核) / verified(已审核) / published(已发布) ← 仅此档公开
    offline(已下架) / invalid(已失效) / rejected(已驳回) / deleted(已删除)

- 非 `published` 档对匿名与搜索引擎一律返回 **404**（**不是 403** —— 403 等于承认「该 id 存在」）；
  sitemap 也不收录。
- **旧列仍在，但只是双写备份，判断可见性一律以 `state` 为准。**
  `status` 只有 `pending` / `approved` / `rejected` 三值、**粒度不够**：
  `verified` 与 `published` 的 `status` **都是 `approved`**，按 `status` 判断会把
  「已审核但还没发布」的条目误当已公开。选这个双写方案是为了回滚到 1.0.75 时数据仍自洽。
- `deleted` **不在**可设置档位里（只有软删除端点能产生），避免误把条目直接置为已删除。

**每次重启都会跑一次状态回填**（`backfillDealState`），这是**幂等**的，且有一条硬不变量：

> 回填只会产出 `deleted` / `invalid` / `rejected` / `pending` / `published`，
> **永远不会产出 `offline` 与 `verified`**。因此库里已是这两个值的行**必定是人工设置的**，
> 回填无权改写（所有步骤都带 `state NOT IN ('offline','verified')` 守卫）。

这条守卫是 1.0.78 才补上的，它防的是一个真实事故（见下节 ①）。

### 🐞 1.0.78 修的两个线上级 bug（都做过线上验证）

**① 每次重启，下架的条目自动重新上线**

回填按旧列重算，而「已下架」行双写的 `status` 仍是 `approved`（下架是主动行为，不改审核结论），
于是被回填算成 `published` —— **容器重启一次，所有下架条目就悄悄回到线上，且没有任何提示**。

本地复现：设为 offline → 重启 → 自动变回 published。
修法即上面的硬不变量。**线上实测：连续重启 3 次，分布纹丝不动**（回填日志出现 4 次，结果不变）。

> 中途我曾改成「用标记只回填一次」，结果 `third-batch-server` 的「旧库升级」用例立刻变红 ——
> 它揭示了那个设计过紧：运营脚本直连 SQLite 导入、只写 `status` 的行是真实存在的
> （本项目就干过：域名渠道批量导入），应当每次启动都能自愈。
> 最终形态是「每次回填 + 守卫保护人工档位」，兼得自愈与安全。

**② 管理员专属控件对「名单型管理员」不渲染**

`/api/auth/me` 与 `/api/auth/login` 只回数据库的 `is_admin` 列，**忽略了 `NUXT_ADMIN_USERS`**；
而服务端其余判定用 `isAdminUser()`（库列 **或** 名单，取或）—— 两边口径不一致。

后果：靠名单授权的管理员，前端 `authStore.isAdmin` 恒为 `false`，**所有管理员专属控件都不渲染**
（新加的状态选择器，以及既有的「精选对比」开关 —— 说明这是**既有**缺陷，非该轮引入），而 API 却放行。
修法：两个端点统一改用 `isAdminUser(user)`。

> 对当前线上**无影响**：生产管理员是 `admin_favs`，库中 `is_admin=1`，
> 所以状态下拉正常可见。此修复是为消除口径不一致与未来用名单授权的隐患。

### ✅ 已结案：详情页偶发渲染成「加载失败」（2026-11-04 定位并修复）

**症状**：持续并发下，若干详情页返回 **HTTP 200**，页内却是兜底文案「加载失败，请稍后重试」；
而 `docker logs` **干净**（0 条 `[SSR Error]`、0 条 `[API Error]`）—— 既不是 5xx，也不是能自证的限流 429。

**根因（本地起 instrumented 实例复现后定位）**，一条链四步：

1. 持续并发把同 IP 的**全站读桶**（`FAVSHUB_RL_SITE_READ_PER_MIN=600`）或**同 IP 并发槽**
   （`FAVSHUB_RL_SITE_CONCURRENCY=24`）打满 → `rateLimitError()` 触发；
2. 它把**中文标签**写进 `X-RateLimit-Reason`（`全站 读接口 每 IP 600 次/分钟`）。
   而 HTTP 头值只能是 ByteString（0–255）；
3. 非 ASCII 头值在**解析响应头**时抛
   `TypeError: Cannot convert argument to a ByteString because the character at index 0 has a value of 20840 which is greater than 255`
   （20840 = `全`）→ 本该是 **429** 的响应变成 **500**；
4. 该失败发生在**响应落盘阶段、不经过 error hook**，所以**服务端零日志**；
   SSR 详情页的内部取数拿到 500 后，`error.data` 不是 `{error}` → 回落成兜底文案「加载失败」。

**复现证据**（同一批 URL、1000 次详情页请求、并发 12，本地 instrumented 实例）：

| | 结果 |
|---|---|
| 修前 | `800 × status=500`（页内「加载失败」），`docker logs` 无痕 |
| 修后 | `800 × status=429`（`Retry-After: 1` + `x-ratelimit-reason: site-read-per-ip`），非 ASCII 头值 0 处 |

**生产验证（1.0.69 上线后）**：

- 容器内直连 app 把读桶打满：700 请求 → **恰好** `600 × 200` + `100 × 429`（阈值 600/分钟，分毫不差）。
  429 的 body 是 `{"error":"超出限频（全站 读接口 每 IP 600 次/分钟）：请在 59 秒后重试"}`，
  头是 `retry-after: 59` + `x-ratelimit-reason: site-read-per-ip`，**无任何非 ASCII 字节**。
- 对详情页连发 2232 次请求（并发 12）：`2034 × 429` + `198 × 200`，**0 个 500、0 个「加载失败」** ——
  同一突发档位在 1.0.68 上是**静默降级**，现在退化成**诚实、可退避的 429**。

**改法**（提交 `57670c8`；只动限流层，不碰业务逻辑 / 接口 / 数据库）：

- `X-RateLimit-Reason` 只写 **ASCII 短码**（`site-read-per-ip` / `site-write-per-ip` / `site-asset-per-ip` /
  `site-ip-concurrency` / `ai-quota` / `ai-token-concurrency` / `ai-ip-concurrency`）；
  人读的中文长文案留在 body 的 `data.error`（客户端契约不变，「错误文案里同时写清秒数」照旧）；
- 新增 `asciiHeader()` 兜底 percent-encode 非 ASCII —— **以后新加的中文标签也不会再炸**；
- **回归断言（第一版是错的，已被独立验证打回并重做）**：
  第一版在 `third-batch-ratelimit` 里加了「响应头全为 ASCII」（+9 项）。独立验证实测：
  **把 `asciiHeader(code)` 改回 `label`、重新构建后，该断言依然 115 项全过、退出码 0** ——
  因为 `rateLimitError()` 外层本就有 try/catch，中文头被**静默丢弃**，客户端收不到非 ASCII 头。
  它咬的是 latin-1 `é` 那类「Node 会接受并真上线」的值，**不是本次这条路径**，
  故按「纵深防御」保留，但标签已改成「无 latin-1 乱码」并注明**不是主证据**。
  真正的门重做在 `third-batch-detail.mjs` 的 **⑨ 段**（+5 项）：把全站读档压到 1/分钟，
  断言「页面**不再**回落成『加载失败』」+「页面诚实展示『超出限频』」+ 状态码语义 +
  源码仍走 `asciiHeader()`。**实测会真的翻转**：

> **教训（写给下一次）**
>
> 1. 「响应头写中文」这类错误**在服务端不留任何日志**，现场只剩**下游用户可见的兜底文案** ——
>    归因成本极高。凡是「**上游日志干净、下游有兜底文案**」的症状，优先怀疑**响应头/协议层**，而不是业务逻辑。
> 2. **限流会掩盖 bug**：排查时先确认「限流到底有没有真的触发过」，别在业务代码里空转。
> 3. `server/plugins/error-handler.ts:27-31` 记录的 2026-10-31「61 个详情页同时找不到接入信息区块 + 页面 500 +
>    事后无任何痕迹」，**与本例是同一失败模式**（限流触发 → 头含中文 → 500 且不走 error hook）。
>    那条注释当年的结论今天被证实：**「无法解释的瞬时 500」往往正来自这种「不走 error hook」的路径。**
> 4. **打限流会把自己打到云 WAF 拉黑**：用本机连发 700 个 API 请求后，本机 IP 连 TLS 握手都过不去
>    （`SSL_ERROR_SYSCALL`），而服务器自己访问一切正常。**验收请从服务器侧跑**，或换源 IP。

### ⚠ 待拍板（不是 bug，是取舍）：SSR 自取数也占访客自己的限流额度

限流中间件只作用于 `/api`，但**详情页 SSR 会内部再取一次** `/api/token-deals/<id>`（另加评论区一次），
这些**服务端自取数按访客 IP 计费**（每看一页约 2 次读额度）。后果：

- 正常访客要触发需要 ≈300 页/分钟，基本无感；
- 但**爬虫 / 批量抓取**会把自己的额度打满，之后**整批页面变 429**（现在至少是诚实的 429，不再静默 500）。

取舍：若把内部自取数豁免，页面就**永远不会因限流而降级**，但也**同时失去「爬虫刹车」**——
那层刹车目前正是由限流顺带提供的。**要不要豁免需要按业务意图拍板，我没有单方面改。**

### ⚠️ 本轮回滚有两个**版本相关**的坑，回滚前必读

**① 回滚到 `1.0.75` 及更早 → 「已审核」与「已下架」条目都会变成公开**

`1.0.75` 及更早**不认 `state` 列**，只读旧四列。而这两档的双写 `status` 都是 `approved`，
且 `deleted_at` / `invalid_at` 均为空 —— 在旧版眼里就是「审核通过且未失效」，于是**会直接出现在前台**。

> **2026-11-05 实测确认（不是推断）**：把生产库副本改出一条 `verified`、一条 `offline`，
> 用 `rollback-1.0.75-*` 镜像起独立容器读该副本 —— **两条都出现在公开列表里**。
>
> 复现方法：把库副本 `docker cp` 进一个 `-e NUXT_DB_PATH=/data/probe.db` 的临时容器再重启。
> **务必先自校验探针库真被读到**（公开条数应 ≈72，若为 10 则是容器自建的空库，结论无效）——
> 我第一次就踩了这个坑：`-v 宿主目录:/data` 被本地路径转换改写成了 `$/mnt/t/data`，
> 挂载根本没生效，而**对照组也 404** 正是暴露它的信号。
>
> 教训：**先验证测试装置本身，再采信它的结论。** 反过来我最初的推理是「`offline` 语义一致、无风险」，
> 实测证明推理是错的 —— 两档都泄露。

- **当前线上安全**：`verified` 与 `offline` 计数**均为 0**（13 条域名渠道尚未置为已审核）。
- **回滚前先查**，非 0 就先把这几条在后台改回「待审核」再回滚：

      SELECT state, COUNT(*) FROM token_deals
      WHERE state IN ('verified','offline') GROUP BY state;

- 其余档位（`published` / `pending` / `rejected` / `invalid` / `deleted`）在旧版下语义一致，无此风险。

**② `1.0.76` / `1.0.77` 不要单独回滚**

这两版缺 `1.0.78` 加的回填守卫，**每次重启都会把 `offline`（已下架）条目复活成 `published`**。
要回就回 `1.0.78` 或 `1.0.79`。

> 双写旧列（`status` / `deleted_at` / `invalid_at` / `invalid_reason`）就是为了让回滚路径存在 ——
> 代价就是上面 ① 这条语义差，故必须写在这里而不是散在提交信息里。

## 为什么用「补丁镜像」而不是完整重建

服务器 `apk add gcc` 走官方源极慢，所以不在服务器上跑完整 `docker build`。

**2026-10-31 补了量化数据**（此前只记「>18 分钟未完成」，看不出是卡死还是慢）：

```
apk add curl  （13 MB）→ 1 分 55 秒   ≈ 113 KB/s
apk add gcc 全套（188 MB）→ 按此速度约 28 分钟
实际跑              → 17 分钟后仍停在 (12/30) Installing gcc
```

**结论：不是卡死，是带宽只有 ~110 KB/s。** 完整 build（apk + `pnpm install` +
`pnpm build`）预计 40–60 分钟，**只可当兜底，不可当常规路径**。
日常仍是「CI 建镜像 → 服务器 `pull`」（pull 走 mihomo 代理，快）。

当前做法是**本机构建 → 只拷贝产物**：

```dockerfile
FROM ghcr.io/huanyu-a/favshub:latest
COPY .output/server/chunks      /opt/favshub/.output/server/chunks
COPY .output/server/index.mjs   /opt/favshub/.output/server/index.mjs
COPY .output/server/package.json /opt/favshub/.output/server/package.json
COPY .output/public             /opt/favshub/.output/public
```

**关键：不拷贝 `node_modules`。** 本机是 macOS（`.node` 为 Mach-O），容器是
alpine（musl x86_64）。把本机的原生模块带进去会报 `Error loading shared library`。
保留基础镜像自带的 musl 版本。

打包时用 `COPYFILE_DISABLE=1 tar czf`，否则 macOS 的 `._*` 文件会让 `docker build`
报 `Unexpected "\x00"`。

## 本地构建的两个必需动作

1. **重签原生模块**（本机 Node 是硬化运行时签名，adhoc 签名的 `.node` 加载会失败）：
   ```bash
   for f in $(find .output/server/node_modules -name "*.node"); do
     codesign -f -s - --entitlements <ent.plist> "$f"
   done
   ```
2. **还原被构建改写的文件**（`build` 会重写这两个，不该提交）：
   ```bash
   git checkout -- public/skills/favshub-data-ops.json server/utils/skill-manifest.ts
   ```

## 验证清单（每次部署后）

> **一键版（推荐）**：`node scripts/post-deploy-verify.mjs`
> 它按顺序跑下面 5 项、逐项判定、**任一项失败即非零退出**。
> 加 `--skip-suites` 只跑 curl 那几项（几秒出结果）。

```bash
# 1) 健康检查（期望 200）
curl -s -o /dev/null -w "%{http_code}\n" https://hao.bx9y.com.cn/api/health

# 2) 公开出口 × 内部字段 全矩阵探针（**判据是 0 失败**；通过数随数据浮动）
#    2026-11-09 实测 18 通过 / 0 失败。别把 18 当固定期望：
#      · `token_keys` 空表时该档记「跳过」（skipped 不计入通过，也不冒充验过）；
#      · 「详情页 SSR」档按库里通告条数抽 3 条，条数少时档数就少。
#    改前的 2 项失败（`token-keys` 与 `Key 页`）是**同名字段假阳性**，本轮查清并修掉：
#    `token_deals.source_url` 是内部留痕（永不下发），`token_keys.source_url` 是原帖地址
#    （对外契约 18 字段之一）。豁免改为**按端点**生效，不再按字段名全局生效。
cd favshub-nuxt && node scripts/public-field-matrix.mjs

# 3) 全量通告「两行可见性」审计（期望 两行都无:0 / 错误:0）
#    这是「API 地址行被误隐藏」那个 bug 的回归哨兵
node scripts/full-deal-row-audit.mjs        # 支持 --base / --limit / --concurrency

# 4) 软 404 回归（期望 404）
curl -s -o /dev/null -w "%{http_code}\n" -H "User-Agent: Mozilla/5.0" \
  https://hao.bx9y.com.cn/collections/nonexistent_xyz

# 5) 关键页面冒烟（期望全 200）
for p in / /tokens /tokens/keys /prompts /collections /tokens/domain; do
  printf "%s " "$(curl -s -o /dev/null -w '%{http_code}' https://hao.bx9y.com.cn$p)"; echo "$p"
done

# 6) 状态口径哨兵（期望：只会打印 {'published'}）
#    刻意用断言而不是打印 —— 一旦有未发布档位漏到公开接口，这里必须**非零退出**。
#    这是「只有 published 对外可见」这条规则的回归哨兵。
curl -s "https://hao.bx9y.com.cn/api/token-deals?limit=200" | python3 -c "
import sys, json
states = {r['state'] for r in json.load(sys.stdin)['deals']}
print('  state 集合:', states)
assert states <= {'published'}, '⚠️ 公开接口出现了未发布档位！'
"
```

### 触及状态/迁移的版本：额外做「重启不回退」

改动过 `state` 回填逻辑的版本（`1.0.76` 起），部署后**连续重启 2–3 次**并比对分布，
确认人工档位（`offline` / `verified`）没有被回填改写：

```bash
# 在服务器上跑；三次输出必须完全一致
for i in 1 2 3; do
  docker compose restart favshub >/dev/null && sleep 14
  python3 -c "
import sqlite3; db=sqlite3.connect('data/favshub.db')
print('  ' + '  '.join('%s=%s' % r for r in db.execute(
  'SELECT state, COUNT(*) FROM token_deals GROUP BY state ORDER BY state')))"
done
```

> 1.0.78 上线时实测：重启 3 次分布均为 `deleted=5 invalid=10 pending=12 published=72 rejected=11`，
> 回填日志出现 4 次而结果不变 —— 幂等成立。

`public-field-matrix.mjs` 是**只读探针**，检查「公开出口 × 内部字段」全矩阵：
token_deals 列表/详情/SSR、prompts、collections、tags、token-keys。
它会把「跳过」单独计数——**跳过不等于通过**，看到跳过要查清原因（2026-10-31 加严：
非 200 或不可解析一律计失败，只有显式 `allowSkip` 才跳过）。

## 生产环境事实

- 服务器：3G RAM / 4 CPU，`/` 约 **9.4G 可用（87% 已用）** —— 磁盘偏紧，清理前先确认是否本项目的

- 备份：每日 03:00 自动（`data/backups/auto-backup-*.db`），保留 7 份 ≈ 29M，
  今日备份 `PRAGMA integrity_check` = **ok**（已验可恢复）
- `dockerd` 走本机 mihomo 代理访问 ghcr.io（境内直连会卡死）
- 改 docker 代理配置会重启该机全部 20 个容器，非必要不要动
