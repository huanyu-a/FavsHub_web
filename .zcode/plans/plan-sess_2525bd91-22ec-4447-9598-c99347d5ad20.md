## 四、关键技术设计（文档主体，先说清要点）

### 4.1 架构：服务器宿主 cron，每 3 小时一轮

```
① 发现 Discover   → 聚合 API /api/latest?limit=100&forum=2,8,3,9（带 UA）+ sitemap.xml lastmod 兜底 + max_tid 游标
② 补全文 Full-fetch → 对新 tid 抓 /topic/<tid> 网页版，取完整首帖正文
③ 分类 Classify   → 规则引擎，顺序 B→C→D→A→E，加正文前 40 字符指纹去重
④ 提取凭证 Extract → 分层正则 → (key, base_url) 配对，标 high/medium/low
⑤ 存活探测 Probe   → 站点预检 → /v1/models → 方案回退 → verdict + confidence
⑥ 发布 Publish     → A 类走 /api/ai/token-deals；B 类写 token_keys；每轮生成静态 feed.xml
```

### 4.2 对 01/02 旧方案的一处修正（文档会写明）

02 文档把「正文 200 字符硬截断」列为不可解约束。**实际可绕开**：游客访问 `/topic/<tid>` 能拿到**完整首帖正文**（实测 `/topic/23684` 首帖明文 CDK 完整可见）。所以流程从「用 API 的 content_text 直接分类」改成「API 快速筛候选 → 补抓 topic 页拿全文」。每 3 小时约 6.2 条新帖，补抓成本可忽略。回复内容游客仍拿不到（这一点未变）。

### 4.4 凭证存活检测协议（文档第七章）

探测优先级（成本优先）：`/api/status` 站点预检 → OpenRouter 专探 `/api/v1/key` → `GET /v1/models`（**只读前 4 KB，因为成功响应可能有 166 KB–751 KB**）→ 换鉴权方案（`x-api-key`/`x-goog-api-key`/`?key=`）→ 仅当全 404 才降级 `POST /chat/completions max_tokens=1`（**唯一花钱的一步**）。

状态机：`unknown → valid → quota_exhausted / rate_limited / invalid`，invalid 后保留 7 天下架。

降误报铁律（全部写进文档）：
- 同一 `(key, base_url)` **连续 2 次**同类失败才判 `invalid`；单次记 `unknown`
- `000`/超时/5xx → `unknown`，**绝不判失效**（实测最大误报源，60 路并发 3.3%~6.7%）
- `403` **永不直接判失效**（Cloudflare 挑战与之同码：403 + `text/html` + `Just a moment...`）
- `401` 需 body 佐证：`未提供令牌` 属**探测构造错误**，要换鉴权重试而非判失效
- `429` 看 body 区分限流 vs 额度耗尽（`credit_balance_exhausted` / `insufficient_user_quota`）

成本：100 条约 25–40 s，500 条约 2–3.5 min，**token 费用 0**，流量约 2.5 MB/500 条。

### 4.5 发布集成（文档第八章）

落点按你选的 **方案 A：hao 站内新增 `/tokens/keys`**。三条数据流：
1. 推广 → 现有 `token_deals`，走 PAT 写 **`pending` 待审**（保留人工闸门，自动爬来的推广 spam 风险高）
2. 存活 key → 新表 `token_keys` + 新 `/api/token-keys`，页面默认**脱敏**，点击揭示才取明文；RSS 与 sitemap **永不包含明文**
3. 入口曝光 → www hero 加第 4 个按钮 + hao 五处导航 + sitemap

新表关键字段：`key_masked`（前6+后4）、`key_hash`（sha256 去重）、`base_url`、`verdict`、`confidence`、`probe_kind`、`http_status`、`error_code`、`consecutive_failures`、`first_seen_at`，`UNIQUE(key_hash, base_url)`。**「探测失败」与「凭证失效」分列两字段。**

写入通道现状（已实测，无需新造）：PAT `favs_ai_` 前缀、`dry_run` 不写库、IP 300/分 + 令牌 600/分、普通令牌 `pending` 而管理员令牌 `approved`。**新表/新列必须同时改两个文件**：`server/database/migrate.ts`（运行时权威 DDL，新表走独立 `createTokenKeysSchema` + 一表一 try/catch）和 `server/database/schema.ts`（Drizzle）。部署 = bump `VERSION` → push → 服务器 `docker compose pull` + `bash deploy.sh`。宿主侧 cron 照抄 `scripts/nexus-sync/sync-nexus.py` 现成模式（`.env.example` + `--dry-run`）。
