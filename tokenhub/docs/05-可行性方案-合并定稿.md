## 一、结论摘要

**技术判定：全链路可行。产品预期：按两条链路分别校准——它们的价值差一个数量级。**

| 链路 | 判定 | 一句话理由 |
|---|---|---|
| **推广信息 → 白嫖通告** | **完全可行，主力产出** | 我要推广板块实测 62/100 是推广，识别规则抽查零误判；写入通道 `POST /api/ai/token-deals` 现成，`token_deals.url` 本来就装推广链接 |
| **key 分享 → 福利 key 网页** | **可行，但属捡漏性质** | 历史样本 11/100 含明文 key，但新取 8 条最新帖 0 条；分享者自述「余额蹬完就下」——失效是常态不是意外。这条链路的价值在「验活 + 聚合」，不在「产量」 |

三个「比想象中容易」和一个「比想象中难」：

1. **「哪些是福利帖」已有确定性答案**（本轮新证据）：论坛程序会自动给回复可见帖注入标准占位文案，聚合 API 原样返回 → 严格正则 6/6 全中、对照组 0 误报。你朋友问的「23217 没写回复领 key 怎么分辨」——**不用你分辨，程序自己标注了**（§2.2）。
2. **200 字截断可绕开**：候选帖逐个回源 `/topic/<tid>`，JSON-LD `articleBody` 是完整首帖全文（实测 1037 字符，含被截断的 CDK），每轮只需补抓约 6-8 个请求。
3. **探测零计费**：全走 `/v1/models` 类只读端点（判定表已用 20+ 端点实测标定）。
4. **比想象中难**：福利放送板块 52% 的帖子不属于任何已知类（闲聊/求助），分类器必须有「其他」兜底 + 人工回流；且 key 产出可能长期个位数——**所以 P0 先跑 7 天拿真实数字，再决定 P1 投入**（本方案最重要的止损闸门）。

**唯一高风险项**：自动回复过 Turnstile（养号模块，P2、显式开关默认关，§9.3），已有完整降级路径，不阻塞任何前置阶段。

## 二、你提的每个问题，逐条回答

### 2.1 「你怎么知道哪些是福利帖子？」

三层信号（证据文档 D.7，板块 2/8/3 各 100 条实测）：

| 层 | 内容 | 实测表现 |
|---|---|---|
| 板块预筛 | 只订阅 `/forum/2` 福利放送 + `/forum/8` 我要推广（可选 `/forum/3`），聚合 API 支持 `?forum=` | 全站 54% 的噪音帖（错误地方+求助问答）直接不看 |
| 规则分类（B→C→D→A→E） | B 凭证 11/100 误判 0；C 回复可见 6/100 误判 0；D 积分发卡见 2.3；A 推广链接板块 8 命中 39/100 抽查 0 误判 | 板块 2 覆盖 48%、板块 8 覆盖 70% |
| 兜底 | 未命中但疑似有价值的进人工审核队列；板块 2 其余 52% 多为闲聊，归 E 类不打扰 | 误判样本可回流成新规则 |

**坑**：互动计数器（views/replies）09-20 起数据断层，任何基于回复数的规则一律不写。

### 2.2 「23217 这种没写『回复领 key』的帖子怎么分辨？」

**作者确实没写——论坛程序替他写了。** bbs1.org 程序渲染 `[回复可见]` 标签时会自动追加标准占位文案，写进帖子原始文本，聚合 API 原样返回。23217 的 `content_text` 实测结尾：`…1000刀鸡蛋 https://cssmapi.fun 🔒 回复后可见 回复本主题后即可查看这部分内容。`

- 严格正则 `\[回复可见\]|回复后可见|回复本主题后即可查看`：板块 2 命中 **6/6**（含 23217），板块 8 对照 100 条 **0 误报**。
- `🔒` 单独不算信号（有帖子拿它当项目符号，精确率降到 86%）。
- 需要逐帖复核时看帖子页 DOM：`nb-editor-reply-visible-locked` 服务端渲染标记，4/4 个 gated 帖命中、对照帖 0。

识别已解决；真正的难点在识别后——**怎么拿到被锁内容**：游客侧服务端不下发，聚合 API 标签泄漏率约 1/6，JSON-LD 全文里也不含（本轮实测确认，87 字符止于占位符）。全覆盖只能靠养号自动回复（§9.3，P2 默认关）。

### 2.3 「积分兑换 key 的帖子怎么分辨？」

站点自带「积分发卡」系统，语义显式，是四类里最可靠的：

- 帖子页 DOM：`.virtual-card-box`（「积分兑换」kicker、「库存 N」「XX 积分/张」）；
- 列表页徽标：`virtual-card-title-status` →「发卡中/发卡结束」（本轮实测板块 2 当前列表 5 处仍在渲染）；
- 关键词兜底（可靠性递减）：`兑换|积分|发卡|卡密|CDK`；`积分` 会与抽奖帖交叉，**徽标优先、关键词兜底**。

处置：积分帖是站内付费不是白嫖资源 → 只记录（标题+链接+价格）进「福利情报」，不提取、不探测。

### 2.4 「key 特别容易失效，怎么办？」

三层防护（全部实测支撑）：

1. **零成本高频探测**：每 3 小时随 cron 复探，全走 `/v1/models` 只读端点不计费；判定表按 20+ 端点实测标定（§7）。
2. **误报防线**：网络层失败（实测 3.3%~6.7% 的 `000`）绝不判失效；`403` 永不直接判失效（CF 挑战/额度耗尽同码）；**dead 需连续 2 次一致结论**（间隔 ≥30s）才生效。
3. **页面语义**（裁决，见 §3）：**通告/feed 里「删除用不了的」**——死 key 永不进通知；**页面上置灰标红保留可筛选**——历史参考 + 误报可自动挽回（dead 每天仍复探 1 次）。

### 2.5 「通告每次发送前得更新，删掉用不了的、增加新的」

发布层是「全量清单快照」模型：每轮 cron 先复探存量 → 更新状态 → 写增量 → feed.xml 与网页从最新快照生成。**每 3 小时一封通告，每一封都是发送前刚验过的新鲜状态**，天然满足，无需额外机制。

### 2.6 「能不能用 RSS 做每 3 小时的通知？」

- linux.sb 无原生 RSS（全 404）；第三方聚合 API（10s 轮询）就是事实上的订阅源。
- **RSS 规范里没有推送**，是拉取模型。可行形态：cron 每 3 小时生成静态 `feed.xml`（nginx 直出），群友用阅读器订阅拉取；**主动推送进群是 Bot 的事**，P2 可选项（NapCat/Telegram/QQ 官方三选一，证据文档 C），架构零差别——feed.xml 是唯一产物，Bot 只是多一个读它的进程。
- 8 条/天的频率在任何渠道都不构成风控。

## 五、系统架构

```
┌──────────── 服务器宿主 cron（0 */3 * * *，Python 脚本，照抄 sync-nexus.py 宿主侧模式）────────────┐
│                                                                                            │

│                                                                                            │
│  ② 富集层  候选帖逐个 GET linux.sb/topic/{tid}（每轮约 6-8 个，常规步骤非降级）                │
│     ├─ JSON-LD(@graph).articleBody → 完整首帖全文（实测 1037 字符，绕过 200 截断）             │
```

### 6.2 凭证提取正则（分层，提取前剔除 `Bearer ` 前缀）

```
主正则：(?<![A-Za-z0-9_\-])(?:sk-(?:or-v1|ant(?:-api\d{2})?|proj|svcacct|admin|live|test)-?|gsk_|xai-|fw_|hf_|pplx-|r8_|csk-|AIza)[A-Za-z0-9_\-]{10,220}
通用：\bsk-[A-Za-z0-9_\-]{20,220}\b
Google 专用（误报最低）：\bAIza[0-9A-Za-z_\-]{35}\b
```

- **不要**把 `sk-` 后的串再按 `-` 切分（New API 服务端自己会切，是它的坑不是我们的）。
- 本样本其他格式（`nvapi-`、`ghp_` 等）0 命中，备查即可。

### 6.3 (key, base_url) 配对置信度

| 级别 | 条件 |
|---|---|
| high | 同代码块/同 JSON 对象/同一行/同表格行内 1 URL + 1 key |
| medium | 行距 ≤3 行，或同段内仅 1 URL + 1 key |
| low | 全文仅 1 URL + N keys（或反之） |
| 前缀启发（猜来源不替代 URL） | `sk-or-`→openrouter.ai、`sk-ant`→api.anthropic.com、`AIza`→generativelanguage.googleapis.com、`gsk_`→api.groq.com/openai/v1、`xai-`→api.x.ai/v1、`fw_`→api.fireworks.ai/inference/v1 |
| 探针消歧 | 候选组合各发一次 `GET /v1/models`，取第一个非 401 的配对（零成本） |

中转站凭证无法反推 base_url（纯随机串），必须与分享文本一起采集。

## 七、凭证存活探测协议

### 7.1 探测序（成本优先）

| 级 | 动作 | 计费 |
|---|---|---|
| 0 | `GET {origin}/api/status`（New API 系公开）预检站点存活 | 0 |
| 1 | 厂商原生只读端点：OpenRouter `GET /api/v1/key` | 0 |
| 2 | `GET /v1/models` + `Authorization: Bearer`，**只读状态行 + 前 4 KB** | 0 |
| 3 | 换鉴权方案重试：`x-api-key`、`x-goog-api-key`、`?key=` | 0 |
| 4 | 仅当 2/3 全 404/405 时降级 `POST /chat/completions max_tokens=1` | **唯一计费步，默认关** |

**必须丢弃 body**：`/v1/models` 成功响应实测可达 751 KB，批量校验不丢 body 带宽放大三个数量级。

### 7.2 判定表与同码歧义

| 判定 | 可观测特征 |
|---|---|
| 无效凭证 | 多数 401；**xAI/Google 为 400**；message 含 invalid/无效/Incorrect/not found |
| 额度耗尽 | **不是 402**：OpenAI 429+`credit_balance_exhausted`；New API 403+`insufficient_user_quota` |
| 限流 | 429，可能带 `Retry-After`；OpenRouter 另有 `X-RateLimit-*` |
| 路径错 | 404；尾斜杠 307（不跟随重定向会误判） |
| WAF | 403 + `text/html` + `Just a moment...` |

仅靠状态码无法区分、**必须读 body** 的 5 组：401(无效)vs401(未提供，属探测构造错误要换鉴权重试)；403 五义（额度/IP白名单/分组/地区/CF）；429 二义（限流/耗尽）；404 二义（路径/未实现）；200 二义（成功/中转站管理 API 鉴权失败，看 `success` 字段）。中转站 `error.type` 由运营者自定义（实测 5 种取值），依赖字面量必然误判。

### 7.3 状态机

```
                      ┌─────────┐  首次探测
      分享入库 ──────▶ │ unknown │────────────┐
                      └────┬────┘            │
                  探测成功 │                 ▼
        ┌──────────────────┼──────────┐  ┌──────────┐ ◀─ 连续 2 次一致 invalid（间隔≥30s）
        ▼         ▼        ▼          ▼  │   dead   │    dead：feed/通告排除 + 页面置灰标红
   ┌────────┐ ┌──────────┐ ┌──────────┐  └──────────┘    页面保留可筛选，每天复探 1 次可挽回
   │ valid  │ │ limited  │ │  quota   │
   └────────┘ └──────────┘ └──────────┘   restricted(403 IP/分组/region)、blocked_by_waf、
        ▲          │            │         endpoint_unsupported → 待确认/人工复核队列
        └──── 复探恢复 ─────────┘         unknown 连续 5 轮未决 → 人工队列
```

### 7.4 降误报规则（全部实测来源）

- `000`/超时/5xx → `unknown` 退避重试，**绝不判失效**（最大误报源，60 路并发实测 3.3%~6.7%）。
- `429` → `limited`；body 含 `credit_balance_exhausted`/`insufficient_user_quota` → `quota`（凭证有效）。
- `403` → 先看 Content-Type：CF → `blocked_by_waf`；额度 → `quota`；IP/分组/region → `restricted`。**永不直接判失效**。
- `401` → body 佐证：`未提供令牌` = 探测构造错误（换鉴权重试）；`无效的令牌`/`Incorrect API key` → invalid 候选。
- `400`（xAI/Google）→ `API_KEY_INVALID` → invalid 候选；其他 → unknown。
- `404` → 排除路径问题后 → `endpoint_unsupported`，不判失效。
- **invalid 需连续 2 次一致**（间隔 ≥30s、必要时换 UA）；401/403 不重试但 60s 后复探 1 次去抖。

### 7.5 并发与成本

| 参数 | 取值 |
|---|---|
| 并发 | 单主机 ≤2（保守），全局 ≤16，同主机间隔 ≥0.5s |
| 退避 | 429 按 `Retry-After` 否则 `min(60s, 2^n×1s)`+jitter；5xx/000 → 1s/4s/10s 最多 3 次 |
| 单轮耗时 | 100 条约 25-40s（单请求跨境 1.37s / 国内 0.3s） |
| token 费用 | **0**（全走 /v1/models；降级计费步默认关） |

### 8.4 数据模型（双表，合并 03 与 04 的字段设计）

```sql
CREATE TABLE IF NOT EXISTS token_keys (
  id TEXT PRIMARY KEY,
  source_tid INTEGER,                -- 来源帖子，可回溯
  source_url TEXT DEFAULT '',
  source_title TEXT DEFAULT '',
  source_author TEXT DEFAULT '',
  key_masked TEXT NOT NULL,          -- 脱敏展示（前6+后4）
  key_hash TEXT NOT NULL,            -- sha256，去重用
  key_encrypted TEXT,                -- 完整 key 加密存储，仅供复探与授权导出，不上页面
  base_url TEXT NOT NULL,
  provider TEXT DEFAULT '',
  models TEXT DEFAULT '[]',
  source TEXT DEFAULT 'post',        -- post | reply_visible | aggregator_leak
  confidence TEXT DEFAULT 'low',     -- 配对置信度 high|medium|low
  verdict TEXT DEFAULT 'unknown',    -- valid|quota|limited|dead|unknown|restricted|blocked_by_waf|endpoint_unsupported
  consecutive_failures INTEGER DEFAULT 0,
  last_probe_at INTEGER,
  first_seen_at INTEGER,
  deal_status TEXT DEFAULT 'published',  -- published|hidden
  note TEXT DEFAULT '',
  created_at INTEGER, updated_at INTEGER,
  UNIQUE(key_hash, base_url)
);
CREATE TABLE IF NOT EXISTS probe_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  credential_id TEXT NOT NULL,
  base_url TEXT NOT NULL,
  probe_kind TEXT NOT NULL,
  http_status INTEGER,
  error_code TEXT DEFAULT '',
  error_message_raw TEXT DEFAULT '', -- 原始错误信息，仅审计，不上页面
  attempt_n INTEGER DEFAULT 1,
  verdict TEXT NOT NULL,
  probed_at INTEGER NOT NULL
);
```

## 九、分阶段实施路线

### 9.1 P0 最小闭环（**不动线上站点**）——七天使门

**范围**：服务器宿主新增 `scripts/tokenhub-crawler/`（Python，照抄 sync-nexus.py 的 `--dry-run`/`--print-config`/`.env.example` 模式）→ 发现 → 富集（JSON-LD 全文 + DOM 复核）→ 分类 → 提取 → 探测全链路；输出本地 SQLite + 静态 feed.xml + 可读日报；**不写 FavsHub，不碰任何站点**。

**验收标准**：
1. 连续跑 7 天 × 8 轮，不报错（单轮 <5 分钟）；
2. key 探测误报率 <5%（判 invalid 的样本人工复查 ≥95% 真失效）；
3. 推广分类在 50 条人工标注边界样本上精确率 ≥90%；23217 型帖 100% 判为 C 类；
4. 至少 5 把 key 完成提取（含 ≥1 把来自 200 字截断之后的全文）与探测；
5. 人为注入 1 把失效 key，验证「连续 2 次一致才判 dead + feed 排除 + 页面置灰可挽回」。

**七天数据回答三个问题**：key 真实产量（决定 P1 值不值）、不养号漏掉多少 gated key（决定 P2 养号开关）、误判率（决定判定表回填）。

### 9.2 P1 接入 hao 站（发布自动化）

**范围**：FavsHub 双表 migrate + 读写端点 + `/tokens/keys` 页面 + 导航/sitemap + www hero 按钮；管道切换为 PAT 写入（先普通 PAT 保留 pending 闸门，跑稳两周可换管理员 PAT）；feed.xml 走 nginx 直出（照 `/tokens/eval/` 的 alias 先例）。

**验收标准**：`/tokens/keys` 可访问可筛选默认脱敏；一条 key 从发帖到上页端到端 <3 小时；`pnpm build` + `pnpm ts:check` 通过（本项目无 lint/单测）；人为构造失效 key 下一轮自动置灰出 feed。

### 9.3 P2 可选模块（全部显式开关，默认关）

1. **登录养号 + 自动回复**（你已选的路线，裁决 #4 后置到此）：
   - **收益上限**：gated 帖占板块 2 的 6/100，其中 1/6 已从聚合泄漏——养号最多解锁剩余 ~5%，且拿到的大概率是别人私钥、很快失效；
   - **风险**：注册必须人工一次（JS 人机验证 + 6 位邮箱验证码，实测脚本不可注册）；回复受 **Cloudflare Turnstile** 保护（`window.turnstile.reset(replyForm…)` 实测存在），必须 Playwright 真实浏览器环境，成功率不由自己掌控；封的是你自己的账号；
   - **若开**：专用小号、≤10 回复/天、`ENABLE_ACCOUNT_FARM=false` 默认关、Turnstile 连续 3 次失败即停并告警转人工队列；登录 POST 是否有隐性验证码属未知，实施时小号实测一次；
   - **降级路径**：养号失效 → 回退「聚合泄漏 + 人工补充队列」，系统其余零改动。
2. **人工补充队列**（P0 就有雏形）：聚合拿不到的 gated 帖生成清单页 + 可选通知，你手动决定。
3. **通知 Bot**：P2 届时三选一（QQ 官方机器人需 ICP 备案+IP 白名单+提审；Telegram 无主体门槛富文本最强但国内可达性存疑；OneBot/NapCat 需专用小号+扫码且官方承认风控）。
4. **LLM 复判**低置信分类（每轮约 6 条，成本几分钱，可选）。
