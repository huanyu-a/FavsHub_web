## 一、背景与目标

### 用户原始诉求（要点）

- 自动爬取论坛获取福利信息，信息获取渠道 1：<https://linux.sb/topic/22897>

## 三、前期侦察已确认的事实

> 每条都来自实测（匿名 GET，未登录、未 POST）。完整证据与 URL 见[配套文档](./02-前期侦察实测证据.md)。

### 3.1 数据源 linux.sb

- 自研 PHP 论坛（页脚 `v9.0` 指向 bbs1.org，`x-powered-by: PHP/8.5.8`），Cloudflare 前置但**无 JS 挑战、无 UA 拦截、无速率限制**（实测 28 次请求无 429，无 UA 也被放行）。
- 站点**没有**原生 RSS/Atom/JSON Feed，也**没有**公开 JSON API（`/rss.xml`、`/atom.xml`、`/feed.json`、`/api/topics` 全部 404；`/forum/2/feed` 这类只是「忽略多余路径段」的板块页）。
- 但 **`/sitemap.xml` 含 13443 个帖子 URL + lastmod，分钟级更新**，可作为新帖发现入口。
- 第三方聚合源 `linuxsb.tux298.com` 是可用入口：
  - `/api/latest?limit=100&forum=N`（站点自称 10 秒轮询；`forum` 支持板块 id 或中文名；`limit` 上限 100，`page` 无效）
  - `/rss.xml`、`/atom.xml`、`/feed.json`（JSON Feed 1.1，50 条）
  - **必须带 User-Agent，否则 403**
- 目标板块：`/forum/2` 福利放送、`/forum/8` 我要推广、`/forum/3` 资源分享；另有 `/forum/1` 错误地方、`/forum/7` 深度思考（游客无权限）。
- **硬约束 1**：游客看不到任何回复内容 —— `replies-login-visible` 是**服务端不下发**，不是 CSS 隐藏，JS 里也没有相关逻辑；「回复后可见」块在游客侧是空壳（`nb-editor-reply-visible-locked`）。
- **硬约束 2（关键发现）**：但聚合 API 返回的是**帖子原始文本**，**包含 `[回复可见]…[/回复可见]` 标签内部的内容** —— 抽样 6 条 gated 帖中有 1 条凭证直接泄漏在 API 里（gated 子集泄漏率 1/6）。同时 **`content_text` 被硬截断在 200 字符**（板块 2 有 27/100、板块 8 有 29/100 的帖子正文正好 200 字）。
- 实测速率：福利放送 ≈ **16.5 帖/天**，我要推广 ≈ **33.1 帖/天**，资源分享 ≈ 7.1 帖/天。
  **合计每 3 小时约 6.2 条新帖** → 抓取量与成本都极小。

### 3.2 分类信号（实测 200 条样本）

- 首帖含 `sk-` 凭证：板块 2 有 **11/100**，板块 8 有 **0/100**；这 11 条**全部同时给了 base_url**（可解析成对）。
- 推广信号：`aff=` / `/sign-up` / `/register` 在板块 8 命中 **39/100**，人工抽查 10 条 **0 误判**；「注册送…」句式命中 37/100。
- 回复可见占位符：板块 2 命中 **6/100**（严格正则）；把 `🔒` 也算进去会引入误判（精确率降到 86%）。
- 积分/发卡：站点有 `.virtual-card-box`（文案「积分兑换」「库存 292」「88 积分/张」「已兑换 150 张」）与列表页 `virtual-card-title-status active`「发卡中」徽标 —— 这是**最可靠的识别特征**。
- 按作者白名单收益低（100 帖 72 个作者，Top5 仅占 19%）；**应按正文指纹去重**（实测发现同一条广告换号重发：板块 8 有 11 组 / 28 帖，且多为不同作者）。
- 互动计数器 09-20 之后整体归零（数据断层）→ **任何基于回复数 / 浏览量的分类规则当前不可用**。

### 3.3 凭证存活校验（实测 20+ 端点）

- 判定语义**高度不统一**：OpenAI 401 `invalid_api_key`；**xAI 与 Google 用 400**；OpenRouter 的 `/v1/models` **完全公开**（带无效凭证也返回 200，**不能**用于校验），必须改探 `/api/v1/key`。
- 「额度耗尽」**不是 402**：OpenAI 用 429 + `credit_balance_exhausted`，New API 系用 403 + `insufficient_user_quota`。
- Cloudflare 挑战是 **403 + `text/html` + `Just a moment...`**，与「凭证被拒的 403」同码 → **403 永不直接判失效**。
- 中转站的 `error.type` 由运营者自定义（实测 5 种不同取值：`v_api_error` / `rix_api_error` / `new_api_error` / `chatanywhere_error` / `api_error`）→ 依赖它必然误判。
- 最大误报源是**网络层失败**：60 路并发实测 3.3%~6.7% 的 `000`（连接失败）。
- New API 系令牌 = `sk-` + 48 位字母数字；**中转站凭证无法反推 base_url**，必须与分享文本一起采集。
- **零成本探测可行**：无效凭证走 `/v1/models` 只走鉴权、不产生计费（实测 401 响应仅 29–281 字节）。

### 3.4 发布与通知（用户已有资产）

- `hao.bx9y.com.cn` = 自研 **FavsHub（Nuxt 3 + Vue 3 + Nitro + SQLite）**，源码在 `D:\project\wwwroot\FavsHub_web\favshub-nuxt`。
- **已有对外写入通道**：`POST /api/ai/token-deals`（需 `favs_ai_` 前缀的 PAT，支持 `dry_run` 预演，限频 600 次/分钟），普通令牌写入为 `pending` 待审，管理员令牌直接 `approved`。
- 表结构 `token_deals(url, call_url, quota, models, region, quality, source_tag, expires_at, note, status, vote_up…)`；`source_tag` 取值 `official|relay|community` —— **「推广信息」的语义已被它覆盖**（现有通告的 `url` 字段装的就是带邀请码的推广链接）。
- 已有一条离线管道 `sync-nexus.py`（**服务器宿主侧** cron，非容器内）把 New API 渠道与评测结果写进 FavsHub 的 `nexus_channels` / `nexus_deal_map` 表 —— 新功能照抄这个模式即可。
- 现有 `is_expired` **只按时间判断**（`expires_at < now`），没有「探测失败」状态位 → 存活检测需要新增字段/新表。
- `nexus.bx9y.com.cn` = New API `v1.0.0-rc.39`；匿名仅暴露 `/api/status`、`/api/about`、`/api/uptime/status`，渠道测试接口（`/api/channel/test`）需管理员身份。
- 通知渠道：每 3 小时 = 8 条/天，**频率在任何渠道都不会触发风控**；RSS 是拉取模型、**不产生推送**（要推送必须自己定时调 Bot API）；QQ 社群主通道只有 OneBot/NapCat（官方承认有风控，需专用小号 + 手机扫码）或 QQ 官方机器人（需 ICP 备案域名 + IP 白名单 + 提审）。
- 当前工作目录 `D:\project\wwwroot\tokenhub` 是**当天新建的空目录**（无任何代码、无 .git），可作为本功能的工程落点。

## 四、工作流拓扑（4 个阶段，最多 8 个子代理）

设计原则：**测量交给代码，判断交给子代理**。所有会被用户当作事实引用的数字，都由脚本里的确定性命令跑出来；子代理只负责设计、解释与挑错。

### 阶段 1｜实测（脚本自己跑，不用子代理）

一条 `node -e` 确定性测量命令（经 `world.run` 执行），一次跑全：

- **样本统计**：三个板块 + 全站各 100 条 —— 凭证命中、推广命中、回复可见命中、链接域名分布、200 字截断率、日均速率、作者集中度、正文指纹去重组数；
- **真实端点探测**（无效凭证 × 约 12 个 host）：状态码 + 错误码 + 判定，用于验证判定表；
- **接口面核查**：`hao /api/token-deals` 公开结构、`hao /api/ai/token-deals` 无令牌应为 401、`nexus /api/status` 版本、`linux.sb/sitemap.xml` 头部、一条游客可见的明文 CDK 帖。

产出：JSON 测量结果，逐行灌进「实测样本」表格卡片，并 `report` 关键数字（防中途失败丢失）。
若命令跑不通（无网络 / 无 node），自动降级为「实测补跑员」子代理用自带工具重跑同一测量并返回同结构结果，脚本会记录降级事实。

### 阶段 2｜四路并行设计（4 个独立子代理，不共享上下文）

每个都拿到阶段 1 的实测基线（避免重复测量），并各自补做自己的实测：

1. **取数工程师** —— 发现 → 取正文的完整链路：聚合 API / sitemap lastmod / 板块 `?sort=post&p=` 三路覆盖对比（游客视角 vs 聚合源视角差异）、增量游标（tid 单调递增）、去重指纹、两个硬约束的影响与规避。
   返回：取数方案 + 实测覆盖率 + 覆盖不到的部分。
2. **分类器设计师** —— 可落地规则（A/B/C/D/E），含正则/字段/优先级/阈值 + 样本上的命中与误判数 + 不确定样本的人工审核队列策略。
   返回：规则表 + 伪代码 + 实测指标。
3. **凭证校验工程师** —— 判定表、状态机（`unknown → valid → quota_exhausted → rate_limited → invalid → recheck`，含自动上下架）、重试退避与并发参数、密钥 + base_url 配对解析、误报控制、成本估算。
   返回：协议 + 判定表 + 状态机 + 已知误报场景。
4. **发布与通知架构师** —— 落点方案对比（≥2 个：FavsHub 新增 `/tokens/keys` 路由 vs 独立子域；推广信息并入 `token_deals` 的轻量改法）、数据模型草案、通知渠道对比与推荐组合、风控注意。
   返回：落点推荐 + 数据模型 + 通知方案。

### 阶段 3｜撰写 + 挑毛病（1 撰写员 + 1 评审员，最多 2 轮）

- 撰写员把四路结论写成完整方案（11 章，中文，含证据表与对比表）；
- 评审员（独立上下文，可回查实测证据）被要求**找失败点而不是点赞**：哪些结论与实测矛盾、哪些没有证据、哪些风险没覆盖、哪些「未知」其实可测而没测；
- 撰写员按意见修订，最多 2 轮。

### 阶段 4｜换人独立复核（1 个全新子代理，没看过前面任何一轮）

只拿最终方案 + 实测 JSON，检查矛盾、无证据断言、遗漏风险、以及「用户会照着做但做不成」的地方。有阻塞问题则撰写员做最后一次定向修订，问题记入 `notCovered`。

> **为什么用两个复核机制**：这份方案会被用来动手建系统，判断错了代价不对称（要写代码、要动线上站点、有封号风险）。所以到「一周目交付一次深度复核」为止，不再叠加更多复核。

### 交付（无阶段标记，纯收尾）

- **主产物卡片**：`artifact.markdown` 发布完整方案（`primary: true`）；
- **看板卡片**：`artifact.table` 展示各板块实测数据，随阶段 1 结果实时出现；
- **`return`**：结论 + findings（逐条带 `verified`/`unconfirmed` 与证据）+ verified（真正跑过的命令）+ notCovered（没能验证的）。

## 五、这份方案会明说做不到的事（不粉饰）

- 游客侧拿不到回复内容，**「回复后可见」的凭证只能靠聚合 API 的标签泄漏 + 200 字截断前的部分**；要全覆盖就得登录养号（有封号风险）—— 方案里单列一节评估，由用户决定是否走。
- 互动量 / replies 类分类规则**当前不可用**（计数器数据断层）。
- 「额度耗尽」「限流」的判定在中转站侧**没有实测样本**，属**文档级**结论，报告里会明确标注。
- 站点速率限制只有 28 次请求的短样本，长期阈值未知。
- 每条帖子正文被 API 截断在 200 字，所有统计是**下界**。
- 聚合源的长期稳定性不由自己掌控（它是第三方服务，且疑似带登录态才能看到 `forum/7`）；自建爬虫是备选但成本更高。

### A.3 方案报告的 11 个章节

1. 结论摘要（可行 / 部分可行 / 不可行 + 3 条理由）
2. 已实测事实（证据表：命令或 URL → 结果）
3. 关键约束（三座大山：200 字截断、回复可见服务端不下发、凭证失效快）
4. 数据链路设计（发现 → 取正文 → 分类 → 提取凭证）
5. 分类器规则表（A/B/C/D/E + 正则 + 优先级 + 实测命中 / 误判）
6. 凭证校验协议（判定表 + 状态机 + 成本 + 误报控制）
7. 发布集成方案（≤2 个备选对比 + 推荐）
8. 通知方案（≤2 个备选对比 + 推荐 + 风控注意）
9. 分阶段实施路线（P0 最小闭环 / P1 / P2，每阶段验收标准）
10. 风险与回滚
11. 关键未知与需人工确认项
