## 一、结论摘要

**总体判定：部分可行。** 必须拆成两条链路分别判定，因为它们的产出量级差了一个数量级。

| 链路 | 判定 | 一句话理由 |
|---|---|---|
| **推广信息 → 白嫖通告** | **完全可行，且高产出** | 我要推广板块实测 62/100 条是推广；识别规则（`aff=`/`/register`/「注册送」句式）零误判；`token_deals.url` 字段**本来就是装邀请码推广链接的**，写入通道 `POST /api/ai/token-deals` 已现成 |
| **key 分享 → 福利 key 网页** | **可行，但产出低、衰减快** | 历史样本 11/100 含明文 key；新取 8 条最新帖 **0 条**；分享者自己在帖子里写「等我号余额蹬完就下」——key 是别人的私钥，被回收是常态不是意外 |

**三条支撑理由：**

1. **数据源侧零阻力**：目标站点有 Cloudflare 但无 JS 挑战、无 UA 拦截、无 429（实测 28 次请求全放行），聚合源日均更新约 50 帖，抓取量与成本都极小。
2. **自动化写入通道已现成**：FavsHub 已有 `POST /api/ai/token-deals`（`favs_ai_` PAT 鉴权 + `dry_run` 预演 + 限频 600 次/分钟），推广类信息的语义已被它覆盖，新功能不需要碰数据库。
3. **key 存活检测可以零成本**：用 `/v1/models` 探测不产生计费（实测无效凭证 401 响应仅 29–281 字节）；但各家状态码语义极不统一（xAI/Google 用 400 不是 401，OpenRouter 的 `/v1/models` 完全公开不能用于校验），必须按判定表分类，且 `403` 永不直接判失效。

**必须说清楚做不到的事**（详见[第十一章](#十一关于登录养号--自动回复的单独评估你选的路线)与[第十三章](#十三关键未知项方案里不能当结论用的)）：
key 链路无法做到「高产出」，它是**捡漏**性质；「回复后可见」的 key 靠聚合 API 泄漏只能拿到约 1/6 且不完整；
登录养号是你自己选的路线，**风险与收益严重不对称**。

## 三、已实测事实（证据表）

> 全部来自匿名只读 GET，未登录、未 POST、未计费。完整证据见 02 文档，这里只列方案依赖的结论。

### 3.1 数据源 linux.sb

| 结论 | 证据 |
|---|---|
| 自研 PHP 论坛（`bbs1.org` 出品），有 Cloudflare 但**无 JS 挑战、无 UA 拦截、无 429** | `curl -A "curl/8.19.0"` / `-A ""` / `-A "python-requests/2.31"` 请求 `/forum/2` 全部 200；28 次请求无 429 |
| 站点**无原生 RSS/Atom/JSON Feed**，也**无公开 JSON API** | `/rss.xml`、`/atom.xml`、`/feed.json`、`/api/topics` 全部 404 |
| **`/sitemap.xml` 含 13443 个帖子 URL + lastmod，分钟级更新** | 开头 `<loc>https://linux.sb/topic/23700</loc><lastmod>2026-09-24T07:19:09Z</lastmod>` |
| 目标板块：`/forum/2` 福利放送、`/forum/8` 我要推广、`/forum/3` 资源分享 | `/forum_list` 全 200；`/forum/7` 游客无权限 |
| 第三方聚合源 `linuxsb.tux298.com` 可用，**必须带 User-Agent 否则 403** | `curl -A "Mozilla/5.0" …/api/latest?limit=100&forum=2` → 200；无 UA → 403 |

| **聚合 API 返回帖子原始文本，包含 `[回复可见]…[/回复可见]` 标签内部内容** | 抽样 6 条 gated 帖有 1 条凭证直接泄漏 |
| **`content_text` 被硬截断在 200 字符** | 板块 2 有 27/100、板块 8 有 29/100 的帖子正文**恰好 200 字**且断句明显 |
| 更新速率：福利放送 ≈16.5 帖/天、我要推广 ≈33.1 帖/天、资源分享 ≈7.1 帖/天 | 100 帖 / 跨度天数推算 |
| **合计每 3 小时约 6.2 条新帖** → 抓取量与成本都极小 | 2+8 板块合计日均 ≈49.6 |

### 3.2 分类信号（实测 200 条样本）

| 指标 | 板块 2（福利放送） | 板块 8（我要推广） |
|---|---|---|
| 首帖含 `sk-` 凭证 | **11/100** | **0/100** |
| 推广信号命中 | 35/100 | **63/100** |
| 回复可见占位符（严格正则） | **6/100** | 0/100 |
| 正文恰好 200 字符（被截断） | 27/100 | 29/100 |
| 正文前 40 字符相同的去重组 | 7 组 / 18 帖 | **11 组 / 28 帖** |

- 上述 11 条凭证帖**全部同时给了 base_url** → 「凭证 + 端点」可配对。
- 推广信号单点强度：`aff=` 板块 8 命中 28 条，`/register` 类 39 条；**`首充` 在 200 条里 0 命中（应剔除）**；`注册` 单用太弱（板块 2 有 23 条只由它驱动）。
- **「32 位以上大写字母数字串」是纯误报源**：板块 8 命中 3 条全是推广链接里的联盟 ID → 精确率 **0/3**，必须剔除。
- **按作者白名单抓取收益很低**（100 帖 72 个作者，Top5 仅占 19%）→ 应按**正文指纹去重**。
- **互动计数器 09-20 之后整体归零**（数据断层）→ 任何基于回复数/浏览量的分类规则**当前不可用**。
- 本次新取 8 条最新帖（tid 23707→23674）：**0 条明文 key**；1 条含代理 CDK（`7HQE-SRZH-RTH6` 等，属 D 类）；其余均为「注册送 $」推广。

### 3.3 凭证存活校验（实测 20+ 端点）

| 结论 | 证据 |
|---|---|
| 多数端点 401；**xAI 与 Google 用 400** | `api.x.ai/v1/models` → 400 `Incorrect API key provided`；`generativelanguage.googleapis.com` → 400 `API_KEY_INVALID` |
| **OpenRouter 的 `/v1/models` 完全公开，不能用于校验** | 带无效凭证也返回 200，751207 B，`CF-Cache-Status: HIT`；必须改探 `/api/v1/key` → 401 `User not found.` |
| 「额度耗尽」**不是 402** | OpenAI → 429 + `credit_balance_exhausted`；New API 系 → 403 + `insufficient_user_quota` |
| **Cloudflare 挑战是 403 + `text/html` + `Just a moment...`，与「凭证被拒的 403」同码** | `api.oaipro.com/api/status` 默认 UA → 403 text/html；换 Chrome UA → 404 |
| 中转站的 `error.type` 由运营者自定义（实测 5 种取值） | `v_api_error` / `rix_api_error` / `new_api_error` / `chatanywhere_error` / `api_error` → 依赖它必然误判 |
| **最大误报源是网络层失败** | 60 路并发实测 3.3%~6.7% 的 `000`（连接失败） |
| **零成本探测可行** | 无效凭证走 `/v1/models` 只走鉴权、不产生计费（401 响应仅 29–281 字节） |
| New API 系令牌 = `sk-` + 48 位字母数字；**中转站凭证无法反推 base_url** | new-api `common/utils.go:229` `keyChars = "0-9a-zA-Z"`；随机串无结构化字段 |
| 单请求延迟基线（无效凭证、不下载 body） | OpenAI 均 1.37 s；Groq 1.15 s；SiliconFlow 0.27 s；Moonshot 0.31 s |

## 四、关键约束

### 三座大山

| # | 约束 | 影响 | 本方案的应对 |
|---|---|---|---|
| 1 | **正文 200 字符硬截断**（聚合 API） | 所有统计是**下界**；200 字之后的凭证完全不可见 | 抓取后**二次请求 `/topic/<tid>` 网页版**取完整首帖正文，绕开截断（见 5.2） |
| 2 | **「回复后可见」服务端不下发** | 游客侧拿不到；`plugins.js` grep `reply-visible` 零命中，非 CSS 隐藏 | 靠聚合 API 的标签泄漏（约 1/6 gated 帖）+ 登录养号模块（你选的，P2、默认关） |
| 3 | **凭证失效快** | 分享的是别人的私钥，回收是常态 | 每 3 小时全量重探 + 状态机 + 自动上下架，这正是「删除用不了的，增加新的」的需求 |

### 两座小山

| # | 约束 | 影响 | 本方案的应对 |
|---|---|---|---|
| 4 | 互动计数器数据断层（09-20 起） | 基于 replies/views 的规则不可用 | 分类器**不使用**任何互动量特征 |
| 5 | 聚合源是第三方服务，长期稳定性不由自己掌控 | 单点依赖 | 用 `/sitemap.xml` lastmod 做**第一方兜底发现**（见 5.1），聚合源只做加速 |

### 5.2 发现与补全文的细节

- **主路**：聚合 API 一次拿 100 条/板块，本地过滤 `tid > watermark`。成本：4 个板块 × 1 请求。
- **兜底**：`/sitemap.xml`（第一方、分钟级 lastmod）diff 出新增 URL。若聚合源挂了，这条仍能工作，只是
  要多抓一次 topic 页。
- **游标**：只存 `max_tid` 一个整数（tid 单调递增，`/topic/999999` → 404 佐证）。板块内乱序极罕见
  （实测逆序 2/99）。
- **频率**：默认 3 小时（对齐你的需求）。可配置为 1 小时，速率侧毫无压力。

**关于 200 字截断的补充**：02 文档曾把它列为「不可解」级别的约束。实际上**可以绕开**——游客访问
`/topic/<tid>` 能拿到**完整首帖正文**（实测 `/topic/23684` 首帖明文 CDK 完整可见）。因此流程不是「用
API 的 content_text 直接分类」，而是「用 API 快速筛选候选 → 对候选补抓 topic 页拿全文」。每 3 小时约
6.2 条新帖，补抓成本约 6 个请求，可忽略。

> 与 [03 方案](./03-可行性方案.md) 的关系：03 的 4.1 节同样给出了「按 tid 回源爬单帖页面」的做法，但把
> 它定位成「聚合源挂掉时的备选」（方案 B）。本文档进一步主张：**补抓应是常规步骤而非降级步骤**——因为
> 200 字截断会漏掉凭证，而凭证提取正是本功能要解决的核心问题。两者不矛盾，是力度差异，实施时取本文档
> 的力度即可。

> 注意：补抓只对**首帖**有效。回复内容游客依然拿不到（这是约束 2，未变）。

### 6.1 覆盖率的诚实结论

| 板块 | 四类规则覆盖 | 未覆盖（E 类） |
|---|---|---|
| 福利放送(2) | ≈48% | **52%** |
| 我要推广(8) | ≈70% | 30% |

**福利放送有一半帖子不属于这四类**，需要「其他/闲聊」兜底类，并允许你后续把误判样本回流成新规则。

### 6.2 凭证提取正则（分层）

```
主正则（提取前先剔除 Bearer 前缀）：
(?<![A-Za-z0-9_\-])(?:sk-(?:or-v1|ant(?:-api\d{2})?|proj|svcacct|admin|live|test)-?|gsk_|xai-|fw_|hf_|pplx-|r8_|csk-|AIza)[A-Za-z0-9_\-]{10,220}
```

- 高置信度通用形态：`\bsk-[A-Za-z0-9_\-]{20,220}\b`
- Google 专用（误报最低）：`\bAIza[0-9A-Za-z_\-]{35}\b`
- **不要**把 `sk-` 后面的 48 位随机串再按 `-` 切分（New API 取令牌时自己会切，我们不要画蛇添足）。
- 实测其他格式（`Bearer`、`sk-ant-`、`nvapi-`、`ghp_`、`xai-`）在本样本**全部 0 命中**，列出备查即可。

### 6.3 「凭证 + base_url」配对策略（按置信度）

| 级别 | 条件 |
|---|---|
| high | 同代码块 / 同 JSON 对象 / 同一行 / 同 Markdown 表格行内同时出现 1 URL + 1 key |
| medium | key 与 URL 行距 ≤ 3 行，或同段内仅 1 URL + 1 key |
| low | 全文仅 1 URL + N keys（或反之） |
| 前缀启发 | 仅猜来源，不替代 URL：`sk-or-`→openrouter.ai、`sk-ant-`→api.anthropic.com、`AIza`→generativelanguage.googleapis.com、`gsk_`→api.groq.com/openai/v1、`xai-`→api.x.ai/v1、`fw_`→api.fireworks.ai/inference/v1 |
| 探针消歧 | 对候选组合各发一次 `GET /v1/models`，取第一个非 401 的配对（**零成本**） |

## 七、凭证存活检测协议

### 7.1 探测流程（成本优先）

| 优先级 | 动作 | 计费 |
|---|---|---|
| 0 | `GET {origin}/api/status`（New API/one-api 系，公开）确认站点存活与 `server_address` | 0 |
| 1 | 厂商原生身份/配额只读端点：OpenRouter `GET /api/v1/key` | 0 |
| 2 | `GET /v1/models` + `Authorization: Bearer`，**只读状态行与前 4 KB** | 0 |
| 3 | 同端点换鉴权方案：`x-api-key`、`x-goog-api-key`、`?key=`（New API 系支持） | 0 |
| 4 | 仅当 2/3 返回 404/405 时，降级 `POST /v1/chat/completions` + `max_tokens=1` | **唯一花钱的一步** |

> **必须丢弃 body**：`/v1/models` 成功响应体可能极大（实测 166 KB – 751 KB），批量校验不丢 body 会让
> 流量放大三个数量级。

### 7.2 判定表

| 类别 | 可观测特征 |
|---|---|
| **无效凭证** | 多数 401；**xAI / Google 为 400**；message 含 invalid / 无效 / Incorrect / not found |
| **有效但额度耗尽** | **不是 402**。OpenAI → 429 + `credit_balance_exhausted`；New API/one-api → 403 + `insufficient_user_quota` + `用户额度不足` |
| **有效但被限流** | 429，可能带 `Retry-After`；OpenRouter 带 `X-RateLimit-*` |
| **端点不存在/路径错** | 404；尾斜杠 **307**（不跟随重定向会误判） |
| **WAF 拦截** | 403 + `text/html` + `Just a moment...` |

**仅靠状态码无法区分、必须读 body 的 5 种组合：**

1. 401（凭证无效）vs 401（未提供凭证）→ 看 message（`未提供令牌` vs `无效的令牌`），属**探测构造错误**要换鉴权重试，**不能判失效**。
2. 403（额度耗尽）vs 403（IP 白名单）vs 403（分组无权）vs 403（地区限制）vs 403（CF 挑战）→ 看 `Content-Type` 与 body 的 `code`。
3. 429（限流）vs 429（额度耗尽）→ 同码，看 body `code` 与 `Retry-After`。
4. 404（路径错）vs 404（中转站未实现路由）→ 换已知通用路由交叉验证。
5. 200（成功）vs 200（鉴权失败）→ 中转站管理 API 会这样，解析 `success` 字段。

### 7.3 状态机

```
unknown ──probe──> valid ──后续 probe 连续 2 次失败──> invalid ──(保留 7 天后)──> 下架
                    │
                    ├──> quota_exhausted（凭证有效，展示为「额度耗尽」）
                    ├──> rate_limited（凭证有效）
                    └──> unknown（000/超时/5xx/CF 挑战 → 永不判失效）
```

### 7.4 降误报规则集

- 同一 `(key, base_url)` 必须**连续 2 次**同类失败（间隔 ≥ 30 s、必要时换 UA）才判 `invalid`；单次失败记 `unknown`。
- `000`/超时/5xx/503 → `unknown`，退避重试，**绝不判失效**（这是最大误报源，实测 3.3%~6.7%）。
- `429` → `rate_limited`；body 含 `credit_balance_exhausted`/`insufficient_user_quota` → 改判 `quota_exhausted`（凭证有效）。
- `403` → 先看 `Content-Type`：CF 挑战 → `blocked_by_waf`；`insufficient_user_quota` → `quota_exhausted`；IP/分组/region → `restricted`。**403 永不直接判失效。**
- `401` → 需 body 佐证：`未提供令牌`/`No token provided` → 属**探测构造错误**（换鉴权方案重试）；`无效的令牌`/`Incorrect API key`/`User not found` 等 → `invalid`。
- `400`（xAI/Google 风格）→ `API_KEY_INVALID` / `Incorrect API key provided` → `invalid`；其他 → `unknown`。
- `404` → 先排除路径问题（去尾斜杠、跟随重定向、试 `/v1beta/models`），仍 404 → `endpoint_unsupported`，**不判失效**。
- 分表记录：`credential_id`、`base_url`、`probe_kind`、`http_status`、`error_code`、`error_message_raw`、`attempt_n`、`verdict`、`first_seen`、`last_probe_at`、`consecutive_failures`。**「探测失败」与「凭证失效」分列两字段**；发布页面只展示 verdict 与置信度，**不展示原始 key**。

### 7.5 并发与成本估算

| 参数 | 取值 | 依据 |
|---|---|---|
| 并发 | 单主机 ≤ 4（保守 ≤ 2），全局 ≤ 16；同主机请求间隔 ≥ 0.5 s | 60 路并发出现 3–7% 连接失败 |
| 退避 | 429 → `Retry-After` 优先，否则 `min(60s, 2^attempt × 1s)` + full jitter；5xx/`000`/超时 → `1s, 4s, 10s` 最多 3 次；401/403 → 不重试，但 60 s 后复探 1 次去抖动 | — |
| 请求量 | 100 条约 110 次；500 条约 550 次 | 含重试 |
| 单轮耗时 | 100 条约 **25–40 s**；500 条约 **2–3.5 min** | 单请求 1.37 s 跨境 / 0.3 s 国内 |
| **token 费用** | **0**（全走 `/v1/models`） | 实测无效凭证无计费 |
| 流量 | 约 2.5 MB / 500 条（只读前 4 KB） | — |

## 九、通知方案（按你的选择：只做网页 + RSS）

### 9.1 为什么「用 RSS 做每 3 小时通知」技术上不成立

**RSS 规范里没有任何推送机制**，客户端必须自己定时拉取（rssboard 规范原文）。所以「每三小时的
通知」在 RSS 语义下只能是「每三小时刷新一份可订阅的清单」。标准化补救是 WebSub，但那需要
hub 支持，收益不抵复杂度。

### 9.2 落地形态

- cron 每 3 小时跑完管道后，**原子写**一个静态 `feed.xml`（RSS 2.0）和一个列表页片段；
- nginx 直接 serve（复用 `/tokens/eval/` 的 alias 模式，`nginx.conf:75-81` 已有先例）；
- **只推增量语义**：feed 的 `pubDate` 取本轮生成时间，条目 = 本轮新增有效项 + 一行统计 + 完整清单链接；
- 成员用任意阅读器订阅，频率低（8 次/天），任何阅读器都不会有压力。

> 若你以后想要真推送，加一个 Bot 调用层即可，**不需要改架构**（管道产物不变，只是多一个消费者）。
> 届时按 02 文档 C 节选：QQ 官方机器人（需 ICP 备案 + IP 白名单 + 提审）、Telegram Bot（无主体门槛）、
> 或 OneBot/NapCat 小号（非官方协议，有风控）。

## 十、分阶段实施路线

### P0：最小闭环（不动线上站点）

**目标**：管道跑通，产出可信的「有效 key 清单 + 推广清单」，人工审核后再决定是否接入站点。

**范围**：
- 服务器宿主新增 `scripts/tokenhub-crawler/`（Python，照抄 sync-nexus.py 结构：`--dry-run` / `--print-config` / `.env.example`）
- ①发现 → ②补全文 → ③分类 → ④提取 → ⑤探测 全链路
- 输出：本地 SQLite（或 JSONL）+ `feed.xml` 静态文件 + 一份可读日报
- **不写 FavsHub，不碰任何站点**

**交付物验收标准**：
1. 连续跑 7 天，每天 8 轮，**不报错**；
2. key 探测**误报率 < 5%**（判定 `invalid` 的样本里，人工复查至少 95% 真的失效）；
3. 推广分类在人工标注的 50 条边界样本上**精确率 ≥ 90%**；
4. 单轮耗时 < 5 分钟（目标 6.2 帖 × 1 补抓 + N 探测）。

### P1：接入 hao 站（发布自动化）

**目标**：管道产物自动进站，失效自动下架。

**范围**：
- FavsHub：新表 `token_keys`（`migrate.ts` 加 `createTokenKeysSchema` + `schema.ts` 同步）+ `pages/tokens/keys.vue` + `server/api/token-keys/`（GET 列表 / POST 写入）
- 5 处导航 + sitemap + www hero 按钮
- 管道改为通过 PAT 调用 `POST /api/ai/token-deals` 与 `POST /api/ai/token-keys` 写入，**不直接写 SQLite**
- 「失效自动下架」：`verdict = 'invalid'` → 列表过滤掉；保留 7 天后物理删除或转历史

**交付物验收标准**：
1. `/tokens/keys` 可访问、可筛选、默认脱敏；
2. 一条 key 从发帖到出现在页面上，**端到端 < 3 小时**（一轮 cron）；
3. 人为构造一个已失效 key，下一轮自动下架；
4. `pnpm build` 通过 + `pnpm ts:check` 通过（本项目无 lint/单测）。

### P2：可选增强（默认关闭）

**目标**：提高 key 覆盖率，加人工兜底。

**范围**：
1. **登录养号 + 自动回复模块**（你选的路线，见下节风险，**默认关**）；
2. **人工补充队列**：聚合 API 拿不到的 gated 帖，生成一份清单推给你，你自己决定要不要手动看；
3. 真推送通道（若要）；
4. 误判样本回流：把你在页面上标记的误判样本变成新规则。

## 十一、「登录养号 + 自动回复」的单独评估（你选的路线）

我在方案里把它放在 P2 且**默认关闭**，需要说清理由——不是敷衍，是这条路的**风险与收益严重不对称**。

**收益侧**：能解锁「回复后可见」的 key。但实测 gated 帖在福利放送只占 6/100，且其中已有 1/6 的
凭证从聚合 API 直接泄漏（17%）。也就是说，养号最多把 6% 的帖子里的 key 拿到手，而其中一部分
本来就能拿到。

**风险侧**：
1. 违反站点规则（「回复后可见」是论坛的增长机制，自动回帖是薅这个机制）；
2. 封号风险，且封的是**你自己的账号**；
3. 可能触发验证码/人机校验，届时自动化中断；
4. 更微妙的一点：**即便拿到 key，它大概率也是别人的私钥**，发到你的群里后很快失效——你为了 6% 里
   的少量 key，承担了账号永久损失的风险。

**如果你仍要做**，最小化风险的形态是：单账号、低频率（≤ 每 3 小时 1 帖）、只回帖不互动、
回复内容带人工审核队列、**绝不并发多号**。我会按这个形态实现，并在脚本里留一个显式开关，
默认 `ENABLE_ACCOUNT_FARM=false`。

## 十二、风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **key 产出远低于预期** | **高** | 页面长期只有个位数有效 key | 已在结论中声明。**P0 先量 7 天再决定是否做 P1**——这是本方案最重要的止损点 |

| **推广 spam 混进 `/tokens`** | 中 | 通告质量下降 | 普通 PAT 写 `pending`，走人工审核闸门；正文指纹去重 |

| **养号模块导致账号被封** | **高** | 你自己的论坛账号没了 | 见上一节 |

- **P0**：删 `scripts/tokenhub-crawler/` + 一条 crontab 行，零残留。
- **P1**：FavsHub 侧全部是**新增**（新表、新路由、新导航项）。回滚 = 服务器 `docker compose` 回退到上
  一个 `VERSION` 镜像；数据表留着无害（新表不被旧代码引用）。
- **管道写入**：所有写入走 PAT + `dry_run`，随时可停。

## 十四、一页总结

- **推广信息链路：做**。规则零误判、写入通道现成、产出高（我要推广板块 62/100），是这条功能里**真正有价值的部分**。
- **key 分享链路：先量再做**。产出低（11/100，新样本 0/8）、衰减快（分享者自己都说「余额蹬完就下」）、检测协议复杂但可零成本。**P0 跑 7 天拿到真实数字，再决定 P1**。
- **存活检测是这条功能的灵魂**，不是附加题。你的原话「删除用不了的，增加新的」正是状态机要解决的：每 3 小时全量重探，`invalid` 自动下架。
- **两个「想不到的容易」**：200 字截断可以靠二次抓 topic 页绕开；推广信息本来就在 `token_deals` 的语义里，不用改表。
- **一个「想不到的难」**：福利放送有一半帖子不属于任何一类，需要「其他」兜底类 + 人工回流。
