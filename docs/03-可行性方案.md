## 一、结论摘要

**判定：可行。** 其中「采集 → 分类 → 提取 → 探测 → 发布 → 通知」主链路完全可行且成本极小；「登录养号 + 自动回复」是**有条件可行**——注册必须人工完成一次，自动回复受 Cloudflare Turnstile 保护，全自动存在被拦的现实风险。

三条理由：

1. **数据获取链路已被实测打通。** 论坛每 3 小时仅新增约 6.2 条帖子（证据文档 D.8），聚合 API 一次 GET 即可拿到（2026-09-24 复核仍 200 可用，最新帖 tid 23707）；备用发现入口 `/sitemap.xml` 分钟级更新。抓取量与成本都可以忽略。
2. **写入与展示通道现成。** FavsHub 已有 PAT 鉴权的 AI 写入接口（`POST /api/ai/token-deals`，支持 dry_run、限频 600 次/分钟），「推广信息」本来就是 `token_deals.url` 的既有语义；福利 key 页面按已拍板决策落在 hao 站新增 `/tokens/keys` 路由，复用现成 SSR / 缓存 / 容器 CI，源码与集成点已逐一确认到文件（见第七章）。
3. **凭证存活探测零成本、判定表已实测。** 全部走 `/v1/models` 类只读端点不产生计费；各家状态码语义不统一的坑（xAI/Google 用 400、OpenRouter `/v1/models` 公开不可用、403 永不直接判失效等）已在证据文档 B 节用 20+ 端点实测标定，照表实现即可。

**最大的风险点只有一个**：回复「回复后可见」帖需要过 Turnstile 人机验证（2026-09-24 补充侦察发现，见第五章）。全自动回复必须依赖真实浏览器环境，成功率不由自己掌控；方案为此设计了完整的降级路径，保证养号路线失效时主链路不受影响。

                        │      与 sync-nexus.py 同位置、同模式            │

  ┌──────────┐   ①采集    ┌──────────┐   │

                               │ ②分类
                          ┌────▼─────┐

                    ③提取  │        │ ④回复可见（C 类）→ 养号回复解锁（第五章）
                          ┌────▼─────┐  │
                          │ 凭证提取器 │  │  正则 + (key, base_url) 配对解析（证据 B.5）

                               │ ⑤探测
                          ┌────▼─────┐

                          └────┬─────┘
                               │ ⑥发布（PAT 写入，不直接碰 SQLite）
                          ┌────▼──────────────────────┐
                          │ FavsHub（hao.bx9y.com.cn）  │
                          │  推广 → POST /api/ai/token-deals（既有通道）│
                          │  key  → POST /api/ai/token-keys（新增）    │
                          │  页面：/tokens（既有）+ /tokens/keys（新增） │
                          └────┬──────────────────────┘
                               │ ⑦通知
                          ┌────▼─────┐
                          │ feed.xml │  cron 生成静态 RSS 2.0 + 网页清单页（P0）

                          └──────────┘

**运行形态**：采集/分类/提取/探测是一个 Node 脚本（本机原生 fetch 已实测可用，证据 F 节），部署在服务器宿主侧跑 cron（照抄 `sync-nexus.py` 的「宿主侧 cron、通过 HTTP API 写库」模式，不进容器、不直接写 SQLite）。工程落点 `D:\project\wwwroot\tokenhub`。

**「通告每次发送前得更新，删掉失效的，增加新的」的满足方式**：发布层永远是「全量清单快照」——每轮 cron 先探测存量 key、更新状态，再写增量；feed.xml 和网页每次都从最新快照生成，天然满足「发送前更新」。

## 四、模块设计（每模块 ≥2 备选对比）

### 4.1 采集

| 方案 | 说明 | 评估 |
|---|---|---|
| A. 聚合 API（主） | `GET linuxsb.tux298.com/api/latest?limit=100&forum={2,8,3}`，带 UA | 已实测可用；`content_text` 含 `[回复可见]` 内部内容（泄漏 1/6）；**硬伤：正文截断 200 字符** |
| B. 直接爬站 | 解析 `/forum/2?sort=post&p=N` 列表页 + 帖子页首帖 | 首帖完整无截断；但多一次请求、HTML 解析易碎（自研论坛改版即断） |
| C. sitemap 增量 | `/sitemap.xml` 13443 帖 + lastmod，分钟级更新 | 适合做「新帖发现」游标与 A 的对账，不适合做正文来源 |

**推荐：A 为主 + C 做增量发现与对账，B 仅在聚合源挂掉时临时启用。** 聚合 API 的 200 字截断是硬约束，但对「分类」够用（绝大多数信号在前 200 字内，证据 D.2/D.9）；需要完整正文时（提取凭证、C 类帖回复解锁）按 tid 回源爬单帖页面，请求量极小。

**增量游标**：tid 单调递增（实测 `/topic/999999` → 404），每轮记录 `max_tid`，下轮只处理 `tid > max_tid` 的新帖。**去重**：按正文前 40 字符指纹去重（实测板块 8 有 11 组 / 28 帖是同广告换号重发，证据 D.4）。

### 4.2 分类

| 方案 | 说明 | 评估 |
|---|---|---|
| A. 纯规则 | 证据 D.7 的规则表（正则 + 优先级 + 实测命中/误判） | 零成本、可解释、命中数据已知；「其他」类覆盖不足（板块 2 有 52/100 未命中） |
| B. LLM 辅助 | 规则先行，低置信样本交 LLM 复判 | 提升覆盖率；每轮约 6 条新帖，成本几分钱；但引入不可解释性与延迟 |
| C. 全 LLM | 每条都过模型 | 无必要，规则已覆盖 48%~70%，且 B/C/D 类是高精度规则 |

**推荐：P0 用纯规则 A（判定顺序 B → C → D → A → 其他，证据 D.7），规则未命中且疑似有价值的进「人工审核队列」；LLM 复判作为 P2 可选项。** 规则要点（全部引自实测）：

- **B 类（凭证分享）**：`sk-[A-Za-z0-9_\-]{20,}`，板块 2 命中 11/100、误判 0；11/11 同时给了 base_url。
- **C 类（回复可见）**：严格正则 `\[回复可见\]|回复后可见|回复本主题后即可查看`，命中 6/100、误判 0；**不要**把 `🔒` 算进去（精确率降到 86%）。
- **D 类（积分发卡）**：优先认站点自带的 `.virtual-card-box` / 「发卡中」徽标（最可靠）；关键词 `兑换|积分|发卡|卡密|CDK` 做兜底（`积分` 会与抽奖帖交叉）。
- **A 类（推广）**：A1 联盟链接（`aff=`/`/sign-up`/`/register`，板块 8 命中 39/100、抽查 0 误判）+ A3「注册送」句式；剔除 `首充`（200 条 0 命中）；`注册` 单用太弱。
- 互动计数器（views/replies）**不可用**（09-20 起数据断层），任何基于回复数的规则一律不写。

### 4.3 凭证提取与配对

直接采用证据 B.5 的分层正则与配对策略，要点：

- 高置信形态负向环视版：`(?<![A-Za-z0-9_\-])(?:sk-(?:or-v1|ant(?:-api\d{2})?|proj|svcacct|admin|live|test)-?|gsk_|xai-|fw_|hf_|pplx-|r8_|csk-|AIza)[A-Za-z0-9_\-]{10,220}`；Google 专用 `\bAIza[0-9A-Za-z_\-]{35}\b` 误报最低。
- **New API 会把 key 按 `-` 切分只取首段**（`middleware/auth.go:401-403`），含 `-` 的 key 发到 New API 系中转站会被截断——提取时保留完整串，探测与展示都不再切分。
- **中转站凭证无法反推 base_url**，必须与分享文本一起采集；配对置信度分 high/medium/low（同代码块 > 行距 ≤3 行 > 全文唯一），配对歧义时用零成本 `GET /v1/models` 探针消歧（取第一个非 401 的组合）。
- C 类帖（回复可见）的凭证在 200 字截断之后时，聚合 API 拿不到 → 进入养号回复流程解锁完整正文后再提取。

### 4.4 存活探测

采用证据 B.2/B.6/B.7 的判定表与协议，不重复展开，实现要点：

- **探测序**：中转站先 `GET /api/status` 预检 → `GET {base_url}/models`（只读状态行 + 前 4 KB，丢弃大 body）→ 鉴权方案回退（`x-api-key` / `x-goog-api-key` / `?key=`）→ 厂商特化（OpenRouter `/api/v1/key`）→ 全 404/405 才降级 `POST /chat/completions max_tokens=1`（唯一计费步骤）。
- **判定铁律**（全部实测来源）：`403` 永不直接判失效（CF 挑战/额度耗尽/IP 白名单同码，先看 Content-Type 与 body）；`429` 先区分限流与额度耗尽（看 body code）；`000`/超时/5xx → `unknown` 绝不判失效；`invalid` 需连续 2 次一致结论（间隔 ≥30s，可换 UA）。
- **并发**：单主机 ≤2、全局 ≤16、同主机间隔 ≥0.5s；一轮 100 条约 25–40s。当前存量按「几十把」设计，单轮探测秒级完成（存量规模属未知项，见第十章）。

### 4.5 发布

已拍板：落 FavsHub `/tokens/keys`。两个备选的完整对比见证据 E.7（独立子域方案 C 因要新建仓库/容器/证书/CI/账号体系被否，塞进 `token_deals` 的方案 B 因语义污染被否）。集成细节见第七章。

### 4.6 通知

已拍板：P0 网页 + RSS。RSS 纯拉取不产生推送（证据 C 节），因此「每 3 小时通知」的 P0 形态是：cron 每 3 小时重新生成静态 `feed.xml`（nginx 直出）+ 清单页；群推送（NapCat / Telegram / QQ 官方机器人三选一，对比表见证据 C）放 P2，推送内容**只推增量**（新增项 + 一行统计 + 完整清单链接）。8 条/天的频率在任何渠道都不构成风控。

## 五、登录养号专节（本方案最大风险点）

> 2026-09-24 补充侦察（匿名 GET，未注册未 POST）：

### 5.1 实测证据

| 环节 | 实测发现 | 对自动化的含义 |
|---|---|---|
| 注册 `/register` | 表单开放（username/password/password2/email），但要求 **JS 人机验证**（`cap-verification-status`「正在加载人机验证…」，需启用 JavaScript）+ **6 位邮箱验证码**（`email_code` required） | **脚本无法完成注册。必须人工注册一次**（需要可用邮箱收码 + 过人机验证），约 5 分钟 |
| 登录 `/login` | 仅 username + password + `_csrf` 隐藏域，无验证码字段 | 可脚本化：POST 表单 + cookie 会话保持（未实测 POST，属文档级推断） |
| 回复 | 帖子页 `.ajax-reply-form`、`#reply textarea[name=body]`，提交走 FormData；JS 源码中出现 `window.turnstile.reset(replyForm…)` | **回复受 Cloudflare Turnstile 保护。纯 HTTP 脚本拿不到 token，必须真实浏览器环境** |

### 5.2 实现设计（P1）

1. **账号**：人工注册专用小号一个（不与任何常用身份关联），凭据存服务器侧本地（不进 git）。
2. **登录会话**：脚本用 cookie jar 维持会话，失效自动重登；登录若被加验证码则告警转人工。
3. **自动回复**：用 **Playwright（持久化用户数据目录，优先有头/类有头指纹）** 完成回复动作以过 Turnstile：
   - 每轮只对「判定为 C 类且值得解锁」的帖子回复（回复内容为固定白嫖用语）；
   - **频率上限：每天 ≤10 次回复**，远低于正常用户水平；发现 Turnstile 反复失败即停止并告警，绝不重试轰炸；
   - 回复成功后回源爬该帖完整正文，提取 `[回复可见]` 块内的凭证。
4. **人工接管队列**：Turnstile 连续 3 次失败、或触发站点验证码、或账号被禁言 → 该帖进「人工补充队列」（网页清单 + 可选通知），由你手动回复/补录。

### 5.3 风险与降级路径

- **风险**：Turnstile 对自动化浏览器可能始终拦截（成功率未知，属本方案最大未知项）；养号行为违反站点规则，账号可能被封；极端情况 IP 被拉黑影响聚合 API 访问（低概率，聚合源是第三方独立服务）。
- **降级路径**（保证主链路不受影响）：养号失效 → 回退「聚合 API 标签泄漏 + 人工补充队列」（即决策 1 的 (a)/(c) 混合方案）。C 类帖覆盖从「全」退到「约 1/6 + 人工」，系统其余部分零改动。
- **明确不做**：不写自动注册脚本；不做验证码打码；不用主号/常用号养号。

## 六、凭证校验协议

完整判定表、最小成本探测序、误报控制规则集见证据文档 B.2 / B.3 / B.6 / B.7，实施照抄即可。此处只列**状态机与数据模型**（与「置灰标红 + 可筛选」决策直接相关）：

```
                    ┌─────────┐   首次探测
        分享入库 ──▶ │ unknown │──────────────┐
                    └────┬────┘              │
              探测成功    │                    ▼
        ┌────────────────┼─────────────┐  ┌──────────┐
        ▼                ▼             ▼  │   dead   │◀─ 连续 2 次 invalid
   ┌────────┐      ┌──────────┐  ┌──────────┐（已失效：页面置灰标红，可筛选）
   │  valid │      │  limited │  │  quota   │
   │（正常） │      │ （限流）  │  │(额度耗尽)│   restricted（403 带 IP/分组/region）
   └────────┘      └──────────┘  └──────────┘   blocked_by_waf（CF 挑战）
        ▲              │             │        endpoint_unsupported（路径不支持）
        └── 后续轮次复探恢复 ──────────┘            │
                                                 ▼
                                             人工复核队列
```

- **所有非 valid 状态都不删除**，页面按状态渲染：`valid` 正常绿、`quota`/`limited` 黄（还有救）、`dead` 置灰标红「已失效」、`unknown`/`restricted` 灰「待确认」；列表提供状态筛选器。
- **复探节奏**：valid/limited 每 3 小时随 cron 复探；dead 降为每天复探 1 次（防误报挽回）；unknown 连续 5 轮未决 → 人工队列。
- **数据模型**（两张新表，写入 FavsHub SQLite，见第七章）：
  - `token_keys`：`id, tid, title, author, key_masked, key_encrypted, base_url, provider, source(post/reply_visible), confidence, status, first_seen, last_probe_at, deal_status(published/hidden), note`
  - `probe_log`：`credential_id, base_url, probe_kind, http_status, error_code, error_message_raw, attempt_n, verdict, probed_at`
- **安全红线**：页面与 feed.xml 只展示 `key_masked`（前 6 位 + 长度）；完整 key 加密存储（`key_encrypted`），仅供你导出使用；`error_message_raw` 不上页面。

- **采集/探测脚本不直接写 SQLite**。PAT 在 FavsHub 管理后台 → API 令牌创建（scope `write`），脚本带 PAT 调 `/api/ai/token-keys`（普通 PAT → pending 待审，管理员 PAT → 直接 approved；建议先用普通 PAT 保留人工闸门，跑稳后换管理员 PAT 全自动）。
- **推广信息**并入既有 `token_deals`：走既有 `POST /api/ai/token-deals`，`source_tag='community'`，零代码改动。
- 采集/探测脚本部署在**服务器宿主侧** cron（`*/3 小时` 一轮），与 `sync-nexus.py` 同机同模式；FavsHub 改动走现有 Docker CI 发布。
- **feed.xml**：宿主 cron 生成静态 RSS 2.0，nginx 直出（照抄 `/tokens/eval/` 的 `alias` 直出模式）。

## 八、分阶段实施路线

### P0 最小闭环（不含养号，纯只读 + 既有通道）

**范围**：采集（聚合 API + tid 游标 + 指纹去重）→ 分类规则表 → 凭证提取 → 存活探测 → FavsHub `/tokens/keys` 上线 → feed.xml。
**验收标准**：
1. 连续跑 3 轮 cron，每轮自动发现新帖并正确分类（人工抽查 20 条分类准确率 ≥90%）；
2. 至少 5 把 key 完成提取与探测，状态正确落库，页面上架；
3. 人为注入 1 把已失效 key，验证「连续 2 次一致才判失效 + 置灰标红 + 可筛选」；
4. feed.xml 每 3 小时更新，包含增量与统计行；
5. 推广类帖子正确出现在 `/tokens`（pending 待审）。

### P1 登录养号 + 自动回复

**范围**：人工注册小号 → 会话保持 → Playwright 自动回复（C 类帖，≤10 次/天）→ 解锁后回源提取 → 人工接管队列页面。
**验收标准**：
1. 小号注册并登录成功，会话可维持 ≥7 天；
2. 至少 1 条 C 类帖通过自动回复解锁并提取到凭证（Turnstile 若通不过，降级路径生效并告警——**这也算验收通过**，但要在方案复盘里记录）；
3. 人工队列有入口、有通知。

### P2 Bot 推送 + 增强

**范围**：通知 Bot（通道三选一，见证据 C 推荐组合）、LLM 复判低置信分类（可选）、聚合源挂掉时自动切直接爬站的兜底。
**验收标准**：群内收到增量通知且格式正确；通知失败有告警。

## 九、风险与回滚

| 风险 | 等级 | 对策 |
|---|---|---|
| Turnstile 拦截自动回复，C 类帖拿不全 | 高（已实测存在该机制） | 人工接管队列；降级回「聚合 API 泄漏 + 人工」（第五章 5.3） |
| 养号小号被封 | 中 | 专用小号、≤10 回复/天、行为拟人；封号即停，走降级路径 |
| 聚合源（第三方）停服 | 中 | sitemap + 直接爬站双兜底；聚合源不可达自动切换并告警 |
| 误判失效把活 key 下架 | 中 | 连续 2 次一致才判 dead；dead 每天复探可自动挽回；页面可筛选不删除 |
| `error.type`/状态码语义误判 | 已标定 | 照证据 B.2/B.6 判定表实现，403 永不直接判失效 |
| 200 字截断漏掉截断后的凭证 | 固有 | C 类走回复解锁；B 类截断后凭证接受遗漏（统计为下界） |
| FavsHub 新表迁移失败 | 低 | migrate 前自动备份 SQLite（admin/backup 已有现成能力）；新表独立，不影响既有功能，回滚 = 还原数据库 + 回退镜像 |
| 探测脚本被中转站风控 | 低 | 全部走只读 `/v1/models`、低并发、UA 规范；唯一计费步骤默认关闭 |

**总回滚方案**：P0 各组件相互独立——脚本停掉即停采集；`/api/ai/token-keys` 是独立端点；`token_keys` 表独立于既有表；页面是独立路由。任一环节回滚都不影响 FavsHub 既有功能。
