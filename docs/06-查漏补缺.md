## 缺口 1：key 页面闭环形态（最重要）

### 问题

05 §8.4 安全红线写「页面只展示 `key_masked`」，「点击复制完整 key」被定为 **P1 之后的可选增强**。但这条链路的产品主张恰恰是「可用凭据」——一个只显示 `sk-abc...xyz` 的页面，群友拿到手没法用。照 05 执行，P1 验收标准「`/tokens/keys` 可访问可筛选」会达成一个「能访问但没用」的页面。这是 05 最大的产品盲区。

### 本轮核实：FavsHub 的揭示设施是现成的

| 设施 | 现状 | 证据 |
|---|---|---|
| 用户体系 | 完整：`users` 表、自助注册（`allow_registration` 配置可关）、JWT httpOnly cookie（`favshub_token`）、首个注册者兜底管理员逻辑 | `server/api/auth/register.post.ts`（`D:\project\wwwroot\FavsHub_web\favshub-nuxt`） |
| 限频 | 现成 `checkRateLimit(key, limit, windowMs)`，IP 级 + 用户名级双重限频，注册端点已在用（默认 10 次/分钟） | `server/utils/rate-limit.ts`、`register.post.ts` 头部 |
| 复制交互 | 组件层已有复制类交互先例（`components/tokens/TokenDealDetail.vue`、`TokenShareSheet.vue` 等） | 见附录 A |

**结论：「登录 + 限频揭示 + 审计」不需要任何新基础设施，是现成组合。**

### 用户拍板：两层组合

| 层 | 适用 | 形态 | 合规含义 |
|---|---|---|---|
| **B 类（已提取到明文 key）** | 帖子明文泄漏 + 聚合 API 泄漏的 key | 页面默认脱敏；**登录后限频揭示完整 key**（揭示端点 `POST /api/ai/token-keys/[id]/reveal`：要求登录态、按 `reveal:{ip}:{userId}` 限频、写揭示审计日志） | 站点经手了凭据内容，风险中等，靠免责声明 + 通知即下架兜底 |
| **C 类（回复可见帖）** | 聚合拿不到内容的 gated 帖 | **不提取、不存储 key**，只记录原帖链接 + 标题 + 「去论坛回复领取」指引 | 零接触 key 内容，合规风险最低；且天然覆盖聚合泄漏拿不到的约 5/6 gated 内容 |

两层组合的额外好处：C 类「只发指引」把 05 §9.3 养号模块的收益上限进一步压低了——gated 内容用户自己回复就能拿，系统没必要替用户过 Turnstile。这强化了 05 裁决 #4（养号后置、默认关）的正确性。

### 对 05 的具体修订点

1. **§一 结论摘要**：key 链路的价值表述补一句「价值兑现依赖揭示端点，脱敏页面无使用价值」。
2. **§8.4 数据模型**：`token_keys` 只装 B 类（明文提取/聚合泄漏）；C 类用轻量记录（可复用 `token_keys` 加 `source='reply_visible_guide'`、`key_masked/key_hash/key_encrypted` 留空，或独立小表——实施时任选其一，倾向前者，少一张表）。
3. **§8.4 安全红线**改写：页面与 feed 默认脱敏不变；「点击复制完整 key」从「P1 后可选增强」**升级为 P1 必做**，形态 = 登录 + 限频 + 审计日志（`reveal_log`：credential_id、user_id、ip、revealed_at）。
4. **§8.5 文件清单**补两行：`server/api/ai/token-keys/[id]/reveal.post.ts`（新增，照抄限频与鉴权模式）；`pages/tokens/keys.vue` 的揭示按钮交互（未登录 → 引导登录）。
5. **§9.2 P1 验收标准**补一条：「未登录只见脱敏；登录后限频揭示可用，超频返回 429；揭示行为有审计记录」。

## 缺口 2：合规风险（05 风险表空白）

### 问题

这些 key 来源不明——可能是分享者自有额度，也可能是泄漏/被盗凭据。站点公开陈列并分发完整 key，客观上是「协助使用他人凭据」。05 §十一 风险表 9 行里没有一行涉及这件事，这是空白不是遗漏小事。

### 修订：§十一 风险表新增一行

| 风险 | 等级 | 对策 |
|---|---|---|
| **转发来源不明凭据（泄漏/被盗可能）** | 中 | ① 两层组合：C 类零接触（缺口 1）；② `/tokens/keys` 页面顶部免责声明（内容来自第三方论坛公开帖，仅供测试，如有侵权请联系删除）；③ 建立「收到权利人/平台通知即下架」流程：揭示审计 + `source_tid` 可回溯，单条下架 = `deal_status='hidden'`（05 表里已有该字段）；④ feed/sitemap 永不包含明文（05 已有红线，保持） |

## 缺口 3：多源适配层（「渠道 1」措辞）

### 问题

用户原始需求写的是「信息获取渠道**1**：linux.sb」——暗示后续有渠道 2/3。但 05 §五 架构的发现层写死 `linuxsb.tux298.com/api/latest`，分类规则里「回复可见占位文案」「发卡徽标」全是 linux.sb 专属信号。将来新渠道进来，发现/富集/分类三层要重写。

### 修订：§五 架构补「来源适配器」抽象（P0 就做，零额外成本）

```
sources/
├── base.py          # SourceAdapter 接口：discover(since) -> [RawPost]、enrich(post) -> FullPost
├── linux_sb.py      # 聚合 API + sitemap 兜底 + JSON-LD 富集（05 现状）
└── <渠道2>.py        # 将来
分类规则分两层：
├── 通用规则（跨来源）：sk- 分层正则（05 §6.2）、推广词表 A1/A2/A3、E 类兜底
└── 来源专属规则：回复可见占位文案、发卡徽标（linux.sb 专属，注册进 linux_sb 适配器）
```

`token_keys.source_tid` 相应扩展为 `(source_id, source_tid)` 复合，P0 只有 `linux_sb` 一个值，无迁移成本。

## 缺口 4：推广去重实锤漏洞

### 问题

05 §五 的去重在爬虫层（正文前 40 字符指纹，针对同文案重发）。但本轮实读 `migrate.ts:218-242` 证实：**`token_deals.url` 字段没有 UNIQUE 约束**。同一推广链接换个文案重发 → 指纹不同 → 穿透爬虫去重 → 重复入库 → 通告页重复展示，压力转嫁给 pending 人工审核。板块 8 实测有「同广告换号重发 11 组/28 帖」，这个漏洞会被真实命中。

### 修订：§8.2 数据流 1 补去重

二选一（实施时任选，倾向前者，不动 FavsHub）：

- **A. 爬虫侧**：POST 前调既有读接口按 url 查存量，存在则跳过（或只更新 `updated_at`）；
- B. FavsHub 侧：`token-deals/index.post.ts` 写入时按 url upsert。

## 缺口 5：群通知形态（已裁决，留痕）

### 评估过的方案

群主的核心场景是「转到群里」，而 RSS 是拉取模型。存在一个比 P2 正式机器人轻得多的中间形态：**钉钉/企业微信群机器人 webhook**——无需账号、无需备案、无风控，一个 URL 就能每 3 小时把验活后的新鲜清单推进群；且 05 §10 自己发现服务器已有钉钉推送实践可直接复用。

### 用户拍板：不做，维持 05 的 P2 安排

**记录在案，防止后续轮次重复争论。** P0 仍只有网页 + RSS；群通知等 P2 的 QQ/Telegram/OneBot 正式选型（05 §9.3-3）。若未来改主意，webhook 方案零架构改动（多一个读 feed.xml 快照的进程），随时可插入。

## 缺口 6：三条小补丁

### 6.1 P0 验收标准 #4 自相矛盾

05 §9.1 验收 #4 要求「至少 5 把 key 完成提取」，但 05 自己实测「最新 8 帖 0 条明文 key」，且七天闸门的初衷就是**量产量**——预设 ≥5 把与闸门逻辑冲突，产量为 0 会被误读为「验收失败」而非「闸门结论」。

**改为条件式**：「7 天内出现 key 则提取成功率 100%（含 ≥1 把来自 200 字截断之后的全文）；产量本身（含 0）作为闸门数据记录，不设下限」。

### 6.2 `probe_log` 无清理策略

05 §8.4 的 `probe_log` 每 3 小时随复探增长（100 条存量 × 8 轮/天 ≈ 800 行/天），无保留策略。**补**：保留 90 天，爬虫每轮顺带清理 `probed_at < now - 90d`（一条 DELETE，照抄 sync-nexus 的宿主脚本模式）。

### 6.3 feed.xml 直出位置未写明

05 §9.2 说「feed.xml 走 nginx 直出」但没说是哪层 nginx（宝塔宿主 443 还是容器内 3090）。**写明**：宿主侧宝塔 nginx，照 `/tokens/eval/` 的 alias 先例（02 文档 E 节：`alias /eval-page/` 宿主直出静态页），不进容器、不改 FavsHub 镜像。
