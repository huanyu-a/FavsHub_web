### B.2 判定表（基于实测）

| 类别 | 可观测特征 |
|---|---|
| **无效凭证** | 多数 401；**xAI / Google 为 400**；message 含 invalid / 无效 / Incorrect / not found |
| **有效但额度耗尽** | **不是 402**。OpenAI → 429 + `credit_balance_exhausted` / `organization_spend_limit_exceeded` / `project_spend_limit_exceeded` / `organization_usage_limit_exceeded`；New API/one-api → 403 + `insufficient_user_quota` + `用户额度不足, 剩余额度: X` |
| **有效但被限流** | 429，可能带 `Retry-After`；OpenRouter 额外带 `X-RateLimit-Limit/Remaining/Reset`；OpenAI 另有 `slow_down`、503 `server_is_overloaded` |
| **端点不存在 / 路径错误** | 404（多为空 body 或纯文本 `404 page not found`）；尾斜杠 307；部分中转站返回 200 + `success:false` |

**仅靠状态码无法区分的组合（必须读 body）：**

1. **401（凭证无效）vs 401（未提供凭证）** —— 需要 body 的 message（`未提供令牌` vs `无效的令牌`），或换鉴权方案重试。
2. **403（额度耗尽）vs 403（IP 白名单）vs 403（分组无权）vs 403（地区限制）vs 403（Cloudflare 挑战）** —— 全部 403。需要 `Content-Type`（CF 是 `text/html` + `Just a moment...`）与 body 里的 `code`/message。
3. **429（限流）vs 429（额度耗尽）** —— 同码。需要 body 的 `code` 与 `Retry-After` 是否存在。
4. **404（路径错）vs 404（中转站未实现该路由）** —— 需要换已知通用路由交叉验证。
5. **200（成功）vs 200（鉴权失败）** —— 中转站管理 API 会出现。需要解析 `success` 字段。

### B.4 批量与限流

| 结论 | 证据 |
|---|---|
| OpenAI：常规 429；突发 `slow_down`；过载 503 `server_is_overloaded`；`Retry-After`「may be present」，缺失时退避 + jitter；不要重试额度/计费类错误 | <https://developers.openai.com/api/docs/guides/rate-limits> |
| OpenAI 限流响应头：`x-ratelimit-limit-requests` / `-tokens` / `remaining-*` / `reset-*` 等 | 同上 |
| OpenRouter：平台与上游限流都返回 429，带 `X-RateLimit-*` 或 `Retry-After`；免费模型 20 RPM / 50 RPD（<10 积分） | <https://openrouter.ai/docs/api-reference/limits> |
| DeepSeek 按**并发**限流（`deepseek-flash` 2500 并发），超限 429，且并发限制以账号粒度计、与 key 无关；文档未提 `Retry-After` | <https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit> |
| **实测无法复现 429**：30 路 / 60 路并发（无效凭证）对 OpenAI 与中转站均只返回 401 → 各家真实 429 阈值本次实测不到 | `seq 1 60 \| xargs -P 60 curl …` → 58×401 + 2×`000` |
| **高并发引入连接层失败（`000`），是误报主要来源** | 60 路并发 OpenAI → 2/60 = 3.3% `000`；60 路并发 `api.gpt.ge` → 4/60 = 6.7%；20 次串行 novita → 2 次 `000`；`api.aihubmix.com` 第 2 次请求 25.02 s 超时 |
| 单请求延迟基线（无效凭证、不下载 body）：OpenAI 均 1.37 s；Groq 1.15 s；SiliconFlow 0.27 s；Moonshot 0.31 s | 各端点 `curl -w "%{time_total}"` 实测 |

**并发 / 退避 / 耗时估算（依据：单请求 ≈1.37 s 跨境 / 0.3 s 国内；重试率 8–12%；全局并发 16 时 60 路已出现 3–7% 连接失败）**

- 并发：单主机 ≤ 4（保守 ≤ 2），全局 ≤ 16；同主机请求间隔 ≥ 0.5 s。
- 退避：429 → `Retry-After` 优先，否则 `min(60s, 2^attempt × 1s)` + full jitter；5xx/`000`/超时 → `1s, 4s, 10s`，最多 3 次；401/403 → 不重试，但 60 s 后复探 1 次去抖动。
- 请求量：100 条约 110 次；500 条约 550 次。
- 单轮耗时：100 条约 **25–40 s**；500 条约 **2–3.5 min**（保守配置 6–9 min）。
- 成本：token 费用 **0**（全走 `/v1/models`）；流量约 2.5 MB / 500 条（只读前 4 KB）。

### B.5 凭证形态与提取

| 结论 | 证据 |
|---|---|
| New API 令牌 = `sk-` + **48 位字母数字**（总长 51），存储时 `TrimPrefix("sk-")` | new-api `common/utils.go:229` `keyChars = "0-9a-zA-Z"`、`:254 GenerateKey() → GenerateRandomCharsKey(48)`；`middleware/auth.go:401` |
| **New API 会把 key 按 `-` 切分后只取第一段** → 含 `-` 的 key（如 `sk-or-v1-…`）会被截断 | new-api `middleware/auth.go:401-403` `key = strings.TrimPrefix(key,"sk-"); parts = strings.Split(key,"-"); key = parts[0]`；one-api `middleware/auth.go:96-98` 同逻辑 |
| New API 在 `/v1/models`、`/v1beta/models`、`/v1/messages` 上额外接受 `?key=`、`x-goog-api-key`、`x-api-key` | new-api `middleware/auth.go:366-386` |
| OpenRouter 强校验 `sk-or-` 前缀；Anthropic 强校验 `sk-ant`；OpenAI 不做前缀校验 | 各端点实测（见 B.1） |
| **中转站凭证本身不含任何来源信息，无法反推 base_url** | new-api `common/utils.go:229-244`（纯随机字母数字，无结构化字段）；one-api `common/random/main.go:23-37` |
| 官方厂商凭证可由前缀映射 base_url | `sk-or-`→openrouter.ai、`sk-ant`→api.anthropic.com、`AIza`→generativelanguage.googleapis.com、`gsk_`→api.groq.com/openai/v1、`xai-`→api.x.ai/v1、`fw_`→api.fireworks.ai/inference/v1 |

**可用提取正则（分层，提取前先剔除 `Bearer ` 前缀）：**

```
(?<![A-Za-z0-9_\-])(?:sk-(?:or-v1|ant(?:-api\d{2})?|proj|svcacct|admin|live|test)-?|gsk_|xai-|fw_|hf_|pplx-|r8_|csk-|AIza)[A-Za-z0-9_\-]{10,220}
```

- 高置信度通用形态：`\bsk-[A-Za-z0-9_\-]{20,220}\b`
- Google 专用（误报最低）：`\bAIza[0-9A-Za-z_\-]{35}\b`
- 注意：`\b` 对 `-` 不成立，建议用上面的负向环视版本；**不要**把 `sk-` 后面的 48 位随机串再切分。

**「凭证 + base_url 成对」解析策略（按置信度）：**

1. 同代码块 / 同 JSON 对象 / 同一行 / 同 Markdown 表格行内同时出现 1 URL + 1 key → high
2. key 与 URL 行距 ≤ 3 行，或同段内仅 1 URL + 1 key → medium
3. 全文仅 1 URL + N keys（或反之）→ low
4. 前缀启发（仅猜来源，不替代 URL）
5. 探针消歧：对候选组合各发一次 `GET /v1/models`，取第一个非 401 的配对（零成本）

### B.6 误报控制

| 结论 | 证据 |
|---|---|
| 网络层失败是实测到的最主要误报源 | 见 B.4（3.3%–6.7% 的 `000`） |
| Cloudflare 挑战 = 403 + `text/html` + `Just a moment...`，与「凭证被拒的 403」同码；换 UA 后行为还会变（403 → 404） | `api.oaipro.com/api/status`（默认 UA）→ 403 `text/html`；加 Chrome UA → 404；`/v1/models` + Chrome UA + 无效 key → 401 |
| 地区限制会让**有效**凭证得到 403；IP 白名单会让有效凭证得到 401 或 403 | OpenAI 错误码文档；new-api `middleware/auth.go:434` → 403 `您的 IP 不在令牌允许访问的列表中` |
| 分组 / 模型白名单会让有效凭证在探测特定模型时被拒 | new-api `middleware/auth.go:460/466` → 403 `无权访问 %s 分组` / `分组 %s 已被弃用` |
| 上游过载会原样透出，与凭证无关 | `api.gpt.ge/api/uptime/status` → 200 / `{"message":"502 Bad Gateway","success":false}` |
| 鉴权方案不匹配会伪造成「凭证无效」 | OpenRouter 非 `sk-or-` 前缀 → `Missing Authentication header`；完全不带凭证 → `No cookie auth credentials found`（第三种语义） |

**降误报规则集（草案）：**

- 同一 `(key, base_url)` 必须**连续 2 次**同类失败（间隔 ≥ 30 s、必要时换 UA）才判 `invalid`；单次失败记 `unknown`。
- `000`/超时/5xx/503 → `unknown`，退避重试，**绝不判失效**。
- `429` → `rate_limited`；若 body 含 `credit_balance_exhausted`/`insufficient_user_quota` 等 → 改判 `quota_exhausted`（凭证有效）。
- `403` → 先看 `Content-Type`：CF 挑战 → `blocked_by_waf`；含 `insufficient_user_quota` → `quota_exhausted`；含 IP/分组/region → `restricted`。**403 永不直接判失效。**
- `401` → 需 body 佐证：`未提供令牌`/`No token provided` → 属**探测构造错误**（换鉴权方案重试）；`无效的令牌`/`Incorrect API key`/`User not found` 等 → `invalid`。
- `400`（xAI/Google 风格）→ `API_KEY_INVALID` / `Incorrect API key provided` → `invalid`；其他 → `unknown`。
- `404` → 先排除路径问题（去尾斜杠、跟随重定向、试 `/v1beta/models`），仍 404 → `endpoint_unsupported`，**不判失效**。
- 分表记录：`credential_id`、`base_url`、`probe_kind`、`http_status`、`error_code`、`error_message_raw`、`attempt_n`、`verdict`、`first_seen`、`last_probe_at`、`consecutive_failures`。**「探测失败」与「凭证失效」分列两字段**；发布页面只展示 verdict 与置信度，**不展示原始 key**。

### B.7 推荐校验协议（草案）

1. **预处理**：从分享文本提取 `(key, base_url)` 对；`base_url` 归一化为 `https://host/v1`（或厂商特有路径）。同主机合并为一批次。
2. **站点存活预检**（仅中转站）：`GET {origin}/api/status`，超时 5 s；5xx/`000` → 本轮该主机全标 `unknown` 并跳过。
3. **主探**：`GET {base_url}/models` + `Authorization: Bearer`，浏览器 UA，`--max-time 20`，跟随重定向，只读状态行 + 响应头 + 前 4 KB。
4. **方案回退**：401 且属「未提供凭证」类 → 依次重试 `x-api-key`、`x-goog-api-key`、`?key=`。
5. **厂商特化**：OpenRouter → `/api/v1/key`；Google → `/v1beta/models?key=`；Anthropic → `/v1/models` + `x-api-key` + `anthropic-version`。
6. **降级**（仅当 3–5 全 404/405）：`POST /chat/completions` + `max_tokens=1`（**唯一花钱的一步**）。
7. **判定与重试**：按 B.2/B.6 分流；最多 3 次；`invalid` 需 2 次一致结论。
8. **落库与发布**：写 `verdict` + `confidence` + `evidence`（status/code/message 摘要，**不含完整 key**）；只发布 `valid` / `quota_exhausted` / `rate_limited`。

### 推荐组合（三层）

- **主通道（面向社群成员）**：QQ 群 → OneBot 11（NapCat，Docker）+ **专用小号**（成员零成本，代价是接受非官方协议风控）；若社群有 TG → Telegram Bot 优先（免费、无主体门槛、富文本最强、限流明确）。

### E.7 落点方案对比

**方案 A：在 hao 站内新增 Nuxt 路由 `/tokens/keys`（推荐用于「存活 key 列表」）**

- 做法：`pages/tokens/keys.vue` + `server/api/token-keys/index.get.ts` + 新表 `token_keys`（或复用 `token_deals` 加 `kind='key'`）+ 复用现有 nginx/容器/CI。
- 代价：**低**。新增 1 page + 1~2 API + 1 段 migrate；导航需在 5 处加链接（`components/sidebar/Sidebar.vue:27`、`components/mobile/MobileBottomNav.vue:27`、`pages/collections/index.vue:20`、`pages/prompts/index.vue:27`、`layouts/admin.vue:33`）+ `pages/tokens/index.vue:11-33` 的 header nav。
- 收益：直接复用现成 SSR+SEO、缓存头、限频、审核流、PAT/MCP 通道、分享卡片（`server/api/ai/token-deals/[id]/card.png.get.ts`）、Docker CI。
- 风险：自动下架逻辑必须自己加。

**方案 B：把福利 key 塞进现有 `token_deals`（加 `kind` 字段）**

- 代价：代码量最低（1 字段 + 列表筛选 + 卡片分支），但**语义污染最重**：`/tokens` 是「免费额度情报」，key 是「可用凭据」，混排会让 53 条通告的排序（默认 nexus 优先）与筛选器（品质/来源/地区）失去意义；且 key 需要脱敏展示与轮换，`note/url/quota` 三个字段装不下。
- 结论：只适合「纯推广信息」，不适合「存活 key」。

**方案 C：独立子域 `keys.bx9y.com.cn`（新服务）**

- 代价：**高**。要新建仓库/容器/证书/CI/nginx vhost，且账号体系要么再造一套，要么跨域调 hao 的 `/api/auth/me`（hao 有 CSP `form-action 'self'`、`frame-ancestors 'none'`，CORS 由 `NUXT_CORS_ORIGIN` 白名单控制，需要改配置）。
- 收益：故障隔离、可独立发布节奏。
- 结论：只有当「福利 key」要做成对外独立产品时才值得。

**方案 D：把 key 池挂到 nexus（New API 侧）**

- 代价：中高。New API 的 `/api/token` 是「给注册用户发自己的 key」，不是「公开展示一批共享 key」；匿名接口只暴露 3 个，任何展示页都得写在 nexus 之外；渠道测试需管理员身份，不能在浏览器侧直连复用。
- 结论：nexus 适合作为**被检测对象 / 上游**，不适合作为展示与发布入口。

**推荐组合：**

1. 「存活 key 页面」→ 方案 A（hao 新增 `/tokens/keys` + 新表，复用容器）。抓取与探测程序在**服务器宿主侧**跑（与 `sync-nexus.py` 同位置、同 cron 模式），只通过 PAT 调 `/api/ai/token-deals` 或新增的 `/api/ai/token-keys` 写入，**不直接写 SQLite**。
2. 「推广类信息并入白嫖通告」→ 复用既有 `token_deals`，只加轻量标记（`kind` 或 `source_tag='promo'`），不改卡片/排序主逻辑；写入走 `/api/ai/token-deals`（普通 PAT → pending 待审，管理员 PAT → 直接 approved），保留人工审核闸门。
3. 入口曝光 → 在 `markflow-wiki/docs/README.md` 的 hero actions 加第 4 个按钮（www 是唯一已链接 hao 与 tool 的门户），并在 hao 的 5 处导航补一项；tool 站导航已有 hao 外链，无需改动。
